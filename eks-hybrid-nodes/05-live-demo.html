온프렘을 시뮬레이션한 환경에서 돌렸다

클라우드 VPC 10.0.0.0/16

  • EKS 1.36, system 노드 2대
  • gateway 노드 2대 (c6in.xlarge, 2개 AZ)
  • Karpenter burst 노드 (m6i, m7i)
  • 클라우드 노드는 VPC CNI 사용
Transit Gateway

시뮬레이션 온프렘 VPC 172.18.0.0/16

  • hybrid 노드 호스트 2대 (m7i.xlarge)
  • GPU 호스트 1대 (g6.xlarge, 데모 3 때만)
  • Pod CIDR 172.17.0.0/16 (Cilium)
  • SSH는 EC2 Instance Connect Endpoint만
프로덕션 구성이 아님
EC2를 hybrid node로 쓰는 것은 지원되지 않고, join하면 hybrid node 요금이 부과됩니다.
실제 구성과의 차이
온프렘 서버 + VPN/Direct Connect로 바뀌고, 달라지는 값은 노드 CIDR과 호스트뿐입니다.

데모가 알려 준 함정 세 가지

1. 조용히 실패하는 Kyverno
background controller에 nodes get 권한이 없으면 에러 없이 annotation이 붙지 않아 B가 A와 똑같이 나왔습니다. Pod/binding은 기본 필터에서 빠져 있어 다시 켜야 합니다.
2. Karpenter는 바로 순위를 매기지 않음
줄일 수 있는 노드에만 순위를 쓰고 갱신에 1~5분이 걸립니다. 꽉 찬 15개에서 바로 줄이면 C가 B와 같아져서 12개 warm-up이 필요했습니다.
3. Pod 요청은 init container까지
Pod의 유효 요청은 컨테이너 합과 가장 큰 init container 중 큰 값입니다. Cilium agent의 100m가 init에 있어 hybrid에 6개만 들어갔습니다.
그 밖에
ClusterPolicy는 deprecated, spec.failurePolicy는 거부되고, 기능을 끄면 Karpenter가 쓴 음수 값을 직접 지워야 합니다.

Istio와 gateway는 함께 쓸 수 있다

검증 항목 (Istio 1.30.6, sidecar 모드)결과
hybrid 노드 Pod에도 sidecar 주입통과 4개 Pod 모두 2/2
클라우드와 hybrid 사이 양방향 호출통과 둘 다 200
STRICT mTLS통과 일반 Pod의 평문 호출은 거부, 메시 호출은 mutual_tls
Istio L7 정책 (/admin 거부)통과 /echo 200, /admin/users 403
이때 Cilium 설정enable-l7-proxy=false, enable-vtep=true 그대로
막히는 것은 Istio가 아니다

참고
최신 Istio는 sidecar를 native sidecar(init container, restartPolicy Always)로 주입합니다.

등록Ingress target-type ip, hybrid Pod 2개172.17.0.202, .48이 healthy, AZ all

gateway 전환부하 중 리더 Pod 삭제인계 4초, 191건 중 실패 1 (재시도 없음)
역할 분담 타깃 등록과 해제는 AWS Load Balancer Controller가 하고, gateway는 VPC 밖 Pod IP까지 가는 경로만 줍니다. 그래서 Pod IP가 라우팅 가능해야 합니다.

반대 방향: 온프렘에서 LB로 들어오면

① internal ALB → 리전 Pod: 20/20
온프렘 → DX/VPN(데모는 TGW) → ALB private IP → VPC CNI Pod
gateway를 거치지 않습니다. 온프렘 DNS가 ALB 이름을 private IP로 풀어야 하므로 Route 53 Resolver inbound endpoint가 필요합니다.
② internal ALB → hybrid Pod: 20/20, 그러나 hairpin
온프렘 → ALB → gateway → 다시 온프렘
동작은 하지만 DX를 두 번 지나 지연과 전송 비용이 늘어납니다. 온프렘 Pod는 온프렘 LB로 받는 편이 낫습니다.
③ hybrid NodePort → 리전 Pod: 실패
온프렘 → hybrid 노드 :30080 → 노드 IP로 SNAT → underlay → 리전 Pod
Pod 출발 트래픽이 아니라 gateway를 타지 않습니다. 리전 노드 SG가 온프렘 노드 CIDR에서 오는 앱 포트를 허용해야 합니다(데모 SG는 443만 허용).
AWS 권장 리전에서 오는 트래픽은 ALB, 온프렘에서 오는 트래픽은 온프렘 쪽 Ingress나 LB로 받습니다. gateway를 쓰면 Cilium L7(Ingress, Gateway API)은 꺼지므로 온프렘은 L4 LoadBalancer나 기존 LB를 씁니다.

정리: 무엇을 확인했고 무엇이 남았나

확인한 것
gateway 전환 3~5초, 온프렘 Pod 보호(B, C), GPU 추론 호출, Istio와 gateway 공존(sidecar), ALB ip 타깃 자동 갱신, 온프렘에서 internal ALB 진입.
