NodePool: 어떤 노드를 허용할까요?

먼저 기본 풀의 역할을 구분하고, 필요한 경우 설정을 펼쳐 보세요

일반 앱을 실행할 자리

  • 범용 워크로드용 기본 NodePool
  • amd64 아키텍처 지원
  • On-Demand 인스턴스만 사용
  • EKS 1.37에서는 Balanced 정책

Spot을 쓰려면 별도 커스텀 풀을 만듭니다.

NodePool YAML 발췌 보기

읽기용 발췌입니다. AWS가 관리하는 기본 풀은 직접 수정하지 않습니다.

YAMLapiVersion: karpenter.sh/v1 kind: NodePool metadata: name: general-purpose spec: template: spec: nodeClassRef: group: eks.amazonaws.com kind: NodeClass name: default requirements: - key: kubernetes.io/arch operator: In values: [amd64] - key: karpenter.sh/capacity-type operator: In values: [on-demand] disruption: consolidationPolicy: Balanced

시스템 Pod를 위한 자리

  • 시스템 컴포넌트 전용 NodePool
  • amd64 및 arm64 아키텍처 지원
  • On-Demand 인스턴스만 사용
  • CriticalAddonsOnly taint 사용

taint를 허용하는 toleration이 있어야 배치 후보가 됩니다.

NodePool YAML 발췌 보기

기본 풀은 직접 수정하지 않습니다. 두 기본 풀 모두 EKS 1.37에서는 Balanced를 사용합니다.

YAMLapiVersion: karpenter.sh/v1 kind: NodePool metadata: name: system spec: template: spec: nodeClassRef: group: eks.amazonaws.com kind: NodeClass name: default requirements: - key: kubernetes.io/arch operator: In values: [amd64, arm64] - key: karpenter.sh/capacity-type operator: In values: [on-demand] taints: - key: CriticalAddonsOnly effect: NoSchedule
NodePool = 허용할 노드의 조건.
Spot·별도 인스턴스 조건은 커스텀 풀에 설정합니다. 기본 풀은 활성화·비활성화만 가능합니다.

apiVersion: eks.amazonaws.com/v1 kind: NodeClass metadata: name: workload spec: role: MyAutoModeNodeRole subnetSelectorTerms: - tags: karpenter.sh/discovery: my-cluster network-type: private securityGroupSelectorTerms: - tags: karpenter.sh/discovery: my-cluster ephemeralStorage: size: 80Gi

예제의 network-type은 직접 붙인 subnet 태그입니다. Private subnet에는 필요한 NAT 또는 VPC endpoint 연결도 준비해야 합니다.

요구가 다를 때 커스텀 풀을 만듭니다

먼저 워크로드 목적을 고르고, requirements에서 바뀐 조건을 확인

앞에서 만든 workload NodeClass를 사용합니다. 네트워크·IAM 준비 후 적용하는 예제입니다.

Compute YAML 보기
compute-optimized.yamlapiVersion: karpenter.sh/v1 kind: NodePool metadata: name: compute-optimized spec: template: spec: nodeClassRef: group: eks.amazonaws.com kind: NodeClass name: workload requirements: - key: eks.amazonaws.com/instance-category operator: In values: [c] - key: eks.amazonaws.com/instance-generation operator: Gt values: ["6"] - key: karpenter.sh/capacity-type operator: In values: [on-demand] limits: cpu: 1000

Compute-optimized 특징

  • CPU 중심 작업에 C 계열을 허용하는 예시
  • 7세대 이상 허용 — 성능·용량은 별도 확인
  • 배치 처리·인코딩 등에서 먼저 측정
  • 이 예제는 On-Demand 선택
Spot YAML 보기
spot-mixed.yamlapiVersion: karpenter.sh/v1 kind: NodePool metadata: name: spot-mixed spec: template: spec: nodeClassRef: group: eks.amazonaws.com kind: NodeClass name: workload requirements: - key: eks.amazonaws.com/instance-category operator: In values: [m, c, r] - key: eks.amazonaws.com/instance-generation operator: Gt values: ["5"] - key: karpenter.sh/capacity-type operator: In values: [spot, on-demand] disruption: consolidationPolicy: WhenEmptyOrUnderutilized

Spot Mixed 특징

  • Spot 우선, 가용 용량에 따라 On-Demand 사용
  • 다양한 카테고리 (m, c, r) 로 Spot 풀 확대
  • 용량 유형을 허용해도 혼합 비율은 보장되지 않음
  • 실제 절감률과 재시작 영향을 함께 측정
중단을 감수할 수 있는 작업부터 시작하고, 여유 용량·분산 배치·재시작 시간을 확인하세요.
Graviton YAML 보기
graviton.yamlapiVersion: karpenter.sh/v1 kind: NodePool metadata: name: graviton spec: template: spec: nodeClassRef: group: eks.amazonaws.com kind: NodeClass name: workload requirements: - key: kubernetes.io/arch operator: In values: [arm64] - key: eks.amazonaws.com/instance-category operator: In values: [m, c, r] - key: eks.amazonaws.com/instance-generation operator: Gt values: ["6"] limits: cpu: 2000

Graviton 특징

  • arm64 호환 앱을 위한 Graviton 예시
  • 허용한 M/C/R 계열 중 조건에 맞는 노드 선택
  • arm64 이미지 또는 multi-arch 이미지 필요
  • 라이브러리 호환성과 앱의 비용·성능을 측정
docker buildx build --platform linux/amd64,linux/arm64 으로 멀티 아키텍처 이미지 빌드
GPU YAML 보기
gpu-nodepool.yamlapiVersion: karpenter.sh/v1 kind: NodePool metadata: name: gpu spec: template: spec: nodeClassRef: group: eks.amazonaws.com kind: NodeClass name: workload requirements: - key: eks.amazonaws.com/instance-category operator: In values: [g, p] - key: karpenter.sh/capacity-type operator: In values: [on-demand] taints: - key: nvidia.com/gpu effect: NoSchedule limits: nvidia.com/gpu: 100 disruption: consolidationPolicy: WhenEmpty

GPU NodePool 특징

  • G/P 계열 중 리소스·드라이버 요구에 맞게 선택
  • On-Demand만 사용 (이 예제의 선택; Spot은 별도 검토 가능)
  • Taint를 허용하는 toleration과 GPU 요청 필요
  • WhenEmpty — 빈 노드의 정리를 검토
GPU 인스턴스는 비용이 높으므로 limits 설정이 중요합니다.

Drift 발생 조건
  • AWS 관리 AMI 업데이트 또는 NodeClass 변경
  • 기존 노드와 맞지 않는 인스턴스 요구사항
  • Subnet/SecurityGroup 변경
  • ephemeralStorage 설정 변경

모든 변경이 Drift는 아닙니다. limits·weight·disruption 변경은 Drift를 유발하지 않으며, 허용 범위를 넓혀도 기존 노드가 계속 맞을 수 있습니다.

프로비저닝 시간 단축을 위한 Best Practices

  • 관리형 AMI 교체 확인
    AWS가 AMI 선택·패치 관리
    # Auto Mode: AMI 선택 필드 없음 # AWS 관리 AMI, SSH/SSM 직접 접근 불가 kubectl get nodeclaims
  • ephemeralStorage 크기 설정
    이미지·로그 용량에 맞게 구성
    # Auto Mode NodeClass 설정 발췌 spec: ephemeralStorage: size: 80Gi
  • 다양한 인스턴스 타입 허용
    가용성 향상, 빠른 프로비저닝
    # NodePool spec: template: spec: requirements: - key: eks.amazonaws.com/instance-family operator: In values: [m7i, m7g, c7i, c7g, r7i] - key: eks.amazonaws.com/instance-size operator: In values: [large, xlarge, 2xlarge]
  • Pod Topology Spread 설정
    워크로드 분산, 안정성 향상
    # Pod spec topologySpreadConstraints: - maxSkew: 1 topologyKey: topology.kubernetes.io/zone whenUnsatisfiable: DoNotSchedule labelSelector: matchLabels: app: my-app
  • PriorityClass로 중요 워크로드 우선
    Preemption 활용
    apiVersion: scheduling.k8s.io/v1 kind: PriorityClass metadata: name: critical-workload value: 1000000 globalDefault: false
  • Disruption Budget으로 안전한 교체
    서비스 중단 최소화
    # NodePool spec: disruption: budgets: - nodes: "20%" schedule: "0 9 * * *" duration: 8h
