Strands Agents, Amazon Bedrock AgentCore, 관측과 평가

에이전트 = 모델 + 도구 + 루프

루프는 SDK에 맡기고, 팀은 도구와 지식에 집중

모델: Amazon Bedrock
목표를 이해하고 다음 행동을 추론하고 계획
도구: Tools (MCP)
지식 검색, DB 조회, 사내 API 호출
지식: Knowledge
약관, 절차, 항목 정의서. 답의 품질을 결정
루프: Agent loop
실행, 관찰, 다음 행동을 목표 달성까지 반복
# strands_agent.py
from strands import Agent, tool

@tool
def search_terms(query: str) -> str:
    """상품 약관에서 관련 조항을 찾는다"""
    return kb_search(query)  # 예시 함수

agent = Agent(
    model="<Bedrock 모델 ID>",
    tools=[search_terms],
    system_prompt="근거 조항을 인용해 답한다",
)
agent("ISA 중도 인출 조건 알려줘")

온톨로지, 쉽게 이해하기

개념, 관계, 어휘, 규칙. 그리고 직접 돌려 본 데모

LLM은 왜 우리 데이터 앞에서 틀릴까

사람이 쓰는 말과 시스템에 저장된 값 사이의 세 가지 간극

고객 (또는 직원)의 질문"미국국채 ETF 중에 보수가 제일 싼 거 뭐예요?"
?
상품 원장에 실제로 저장된 값ast_cls = 'BD_OVS_GOV'
rgn_cd = 'US'
fee_bp = 5
말의 간극
"미국국채", "미국채", "US Treasury"는 같은 것. DB에는 BD_OVS_GOV 하나뿐입니다.
관계의 간극
미국국채는 해외국채이고, 해외국채는 채권입니다. 이 계층은 테이블 어디에도 적혀 있지 않습니다.
상식의 간극
"보수"는 fee_bp이고 단위는 bp(0.01%p). 담당자는 알지만 DB는 말해 주지 않습니다.

온톨로지 = 개념, 관계, 규칙의 약속

탭을 눌러 은행 예시로 확인

무엇이 있는가
업무에 등장하는 "종류"를 정합니다. 종류(클래스)와 그 종류에 속하는 실제 하나하나(인스턴스)를 구분합니다.
비유: 사전의 표제어
고객계좌상품자산분류운용사
클래스 고객의 인스턴스: 홍길동, 김민지 ...
클래스 상품의 인스턴스: SKY 미국채10년, RIVER 코스피200 ...
어떻게 이어지는가
개념과 개념 사이에 이름 붙은 연결을 정합니다. 방향이 있고, 어떤 종류끼리 이어지는지도 정합니다.
비유: 지도의 길
고객 보유 계좌
계좌 편입 상품
상품 자산분류 자산분류
상품 브랜드 브랜드, 브랜드 운용사 운용사
무엇은 반드시 지켜지는가
항상 참이어야 하는 제약과 업무 규칙입니다. 모델이 추측하지 않도록 시스템이 강제할 수 있습니다.
비유: 규정집
상위, 하위: 미국국채는 해외국채이고, 해외국채는 채권이다
단일값: 상품의 자산분류는 하나뿐이다
상호배타: 주식이면서 채권일 수는 없다
업무 규칙: "배당"은 분배율로 비교한다

모든 지식을 세 단어 문장으로

주어, 관계, 목적어(트리플)를 하나씩 쌓으면 지식 그래프

버튼을 눌러 트리플을 하나씩 쌓아 보세요.
실선 테두리: 인스턴스(실제 하나)
점선 테두리: 클래스(개념, 종류)
모든 이름과 계좌는 가상 예시

계층이 있으면 "채권"이 저절로 풀린다

개념을 누르면 하위 개념과 해당 상품까지 함께 포함

개념 노드를 눌러 보세요예: "채권 ETF 보여줘". DB에 "채권"이라는 값은 없지만 계층을 따라가면 상품까지 이어집니다.
점선 테두리: 개념(클래스), 실선: 상품(인스턴스). 데모용 가상 ETF 22개 중 이 계층에 연결된 20개만 표시

사람의 말을 DB 값으로 확정하는 사전

대표 이름(prefLabel), 별칭(altLabel), 실제 값을 한 개념에 묶는 어휘(SKOS)

# etf_ontology.ttl (데모에 실제로 쓴 파일 일부)
ex:BdUSGov  a skos:Concept ;
    skos:broader   ex:BdOvsGov ;        # 상위: 해외국채
    skos:prefLabel "미국국채" ;
    skos:altLabel  "미국채", "미 국채", "US Treasury" ;
    ex:sqlFilter   "ast_cls = 'BD_OVS_GOV' AND rgn_cd = 'US'" .

# 업무 상식 (Semantic Layer)
ex:RuleFee  ex:trigger "보수" ;
    rdfs:comment "fee_bp 단위는 bp(1bp = 0.01%p)다. 0.1% = 10bp." .
질문 속 말: "미 국채 ETF 중 보수가 낮은 것"
사전 조회 (LLM 호출 없음)
개념 확정: 미국국채 (상위: 해외국채, 채권)
개념에 붙은 값
조건 확정: ast_cls = 'BD_OVS_GOV' AND rgn_cd = 'US', 규칙: 보수는 fee_bp(bp)
사전에 없는 말이면 추측하지 않고 되묻습니다. 미래에셋증권은 vocabulary.ttl로 같은 일을 합니다.

온톨로지가 에이전트에서 일하는 네 자리

질문이 들어와서 답이 나가기까지, 모델이 추측하던 일을 하나씩 결정적으로

질문 들어옴근거와 함께 답 나감
1
의도 이해
"결제 취소"와 "결제 실패"처럼 비슷한 의도를 속성으로 쪼개 구분
신한카드: Domain, Action, Tag 3속성 인텐트 온톨로지
2
값 확정
사용자의 말을 DB에 있는 실제 값으로 바꾸고, 못 바꾸면 되묻기
미래에셋증권: Ontology Grounding, vocabulary.ttl
3
관계 탐색
여러 관계를 따라가야 답이 나오는 질문을 그래프 조회로
미래에셋증권: Neptune 관계, 시점 조회 / 5부 데모 앱: multi-hop

규칙 강제

Amazon Neptune
관리형 그래프 DB. 속성 그래프(Gremlin, openCypher)와 RDF(SPARQL)를 모두 지원. 관계와 multi-hop 조회가 많아질 때.
Bedrock Knowledge Bases GraphRAG
S3 문서에서 엔터티와 관계를 자동으로 뽑아 Neptune Analytics 그래프로. 벡터 검색 결과를 그래프로 넓혀 답합니다.
GraphRAG Toolkit (오픈소스)
그래프 구축과 검색을 직접 설계하고 싶을 때. 미래에셋증권은 Phase 1에서 이 도구로 Ontology, ER, Search 방법론을 검증했습니다.
출처: Amazon Neptune 문서(What is Amazon Neptune), Bedrock 문서(Build a knowledge base with Amazon Neptune Analytics graphs). GraphRAG는 2026-10-21 문서 기준 서울 리전 목록에 없음: 도입 전 리전 확인 필요
