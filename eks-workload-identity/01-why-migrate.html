세 Pod의 호출이 같은 노드 세션으로 보입니다.

EC2 인스턴스 프로파일은 노드 IAM 역할을 인스턴스에 전달합니다. 인스턴스 안에서 IMDS(169.254.169.254)를 호출하면 그 역할의 임시 자격 증명을 받습니다. IMDSv2는 먼저 PUT으로 세션 토큰을 받은 뒤 그 토큰으로 자격 증명을 조회합니다.

Pod가 이 경로에 닿을 수 있으면, SDK는 다른 공급자를 찾지 못했을 때 IMDS까지 내려가 노드 역할을 씁니다.

노드 역할 공유의 세 가지 위험

권한 범위가 노드 단위

한 앱에 필요한 권한이 그 노드에 스케줄되는 모든 Pod의 권한이 됩니다.
어떤 Pod가 영향을 받나

감사 로그로 구분 불가

CloudTrail 호출자는 노드 역할 세션 하나입니다. 워크로드별 추적과 회수가 어렵습니다.
CloudTrail에서 무엇이 보이나

hop limit 2면 일반 Pod도 IMDS에 닿음

hostNetwork가 아닌 Pod도 IMDSv2 토큰을 받아 노드 역할을 가져갑니다.
hop limit이란
목표: 앱 권한은 워크로드 전용 역할로 옮기고, 노드 역할에는 노드 운영에 필요한 권한만 남긴 뒤 Pod의 IMDS 경로를 닫습니다.

노드 역할은 노드 하나에 하나입니다. 스케줄러는 권한을 보고 Pod를 배치하지 않으므로, 앱 권한을 노드 역할에 붙이면 그 노드 그룹에 뜨는 모든 Pod가 같은 권한을 갖게 됩니다. 결제 Pod를 위한 S3 읽기가 로그 수집기와 배치 Job에도 열립니다.

EC2 인스턴스 프로파일로 받은 자격 증명의 세션은 노드 역할과 인스턴스 ID로 기록됩니다. 같은 노드의 Pod가 모두 같은 세션을 쓰므로 어느 워크로드가 호출했는지 로그만으로 구분하기 어렵습니다. S3 객체 접근을 CloudTrail에서 보려면 버킷의 데이터 이벤트도 켜야 합니다.

IMDSv2는 PUT 요청으로 세션 토큰을 먼저 받습니다. hop limit은 이 토큰 응답이 지날 수 있는 홉 수입니다. 일반 Pod는 노드와 다른 네트워크 namespace에 있어 한 홉이 더 필요하므로, 값이 2 이상이면 Pod도 토큰을 받습니다.

관리형 노드 그룹의 launch template이 이 값을 2로 두는 경우가 많습니다. 이전을 마친 뒤 1로 내려 일반 Pod의 경로를 닫습니다. hostNetwork Pod는 노드 네트워크를 그대로 쓰므로 hop limit과 관계없이 IMDS에 닿습니다.

Pod의 자격 증명은 세 곳에서 온다

node (IMDS)
IMDSv2에서 노드 역할
IRSA (STS)
IAM Roles for Service Accounts. Pod가 리전 STS(Security Token Service)를 직접 호출
Pod Identity
같은 노드의 Agent가 EKS Auth 호출

SDK는 위에서부터 찾고, 처음 것을 쓴다

바뀌는 것은 코드가 아니라 주입된 변수

경로Pod에 주입되는 것SDK가 호출하는 곳결과 역할
node (IMDS)없음IMDSv2 169.254.169.254노드 IAM 역할 (노드의 모든 Pod가 공유)
IRSA (STS)AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE, 토큰 볼륨리전 STS AssumeRoleWithWebIdentityServiceAccount 주석의 역할
Pod IdentityAWS_CONTAINER_CREDENTIALS_FULL_URI, AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE, 토큰 볼륨같은 노드의 Agent 169.254.170.23association에 지정한 역할
주입은 Pod 생성 시점에만: 이미 실행 중인 Pod는 바뀌지 않으므로 설정 후 rollout으로 Pod를 새로 만듭니다.
확인은 호출자 ARN으로: 호출 성공만으로는 부족합니다. 노드 역할로 성공했을 수도 있습니다.

변수는 누가, 언제 넣나: API 서버의 mutating 웹훅

  1. Pod 생성 요청 rollout → ReplicaSet 컨트롤러가 API 서버에 Pod CREATE
  2. 인증·인가 API 서버가 요청자를 확인
  3. Mutating admission: iam-for-pods.amazonaws.com
    EKS가 컨트롤 플레인에서 운영하는 웹훅(amazon-eks-pod-identity-webhook)이 Pod의 ServiceAccount를 봅니다.
    association 있음 → AWS_CONTAINER_* 두 개 + 토큰 볼륨(aud pods.eks.amazonaws.com)
    주석만 있음 → AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE + 토큰 볼륨(aud sts.amazonaws.com)
    둘 다 있음 → Pod Identity만 · 아무것도 없음 → 그대로
  4. Validating admission → etcd 저장 Pod Security 등 검사 후 저장. 이때 Pod 스펙은 이미 바뀌어 있음
  5. kubelet projected 토큰을 해당 audience로 발급받아 파일로 마운트하고 만료 전에 갱신
  6. 컨테이너 시작 SDK가 환경 변수를 읽고 앞 슬라이드의 체인을 탑니다
# 데모 클러스터에서 확인한 웹훅 설정
$ kubectl get mutatingwebhookconfiguration \
    pod-identity-webhook -o yaml
name: iam-for-pods.amazonaws.com
clientConfig.url: https://127.0.0.1:23443/mutate
rules: CREATE pods
failurePolicy: Ignore
objectSelector: eks.amazonaws.com/skip-pod-identity-webhook 없음
CREATE에서만 동작: 실행 중인 Pod는 바뀌지 않습니다. 설정 뒤에는 rollout.
failurePolicy: Ignore: 웹훅이 응답하지 못하면 변수 없이 Pod가 만들어져 조용히 노드 역할로 동작합니다. 그래서 호출자 ARN으로 확인합니다.
미리 확인: kubectl create --dry-run=server로 Pod 템플릿을 보내면 웹훅을 거친 결과를 Pod를 만들지 않고 볼 수 있습니다.
출처: 데모 클러스터(EKS 1.36)의 MutatingWebhookConfiguration, amazon-eks-pod-identity-webhook, Understand how EKS Pod Identity works
