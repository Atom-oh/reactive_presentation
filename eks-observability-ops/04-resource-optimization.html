Vertical Pod Autoscaler & Auto Mode

VPA와 Auto Mode의 시너지 효과

VPA

  • Pod CPU/Memory 사용량 관찰
  • requests 추천 (limits는 기존 비율 유지)
  • Recreate 또는 InPlaceOrRecreate로 적용
  • CPU: 24h 반감기, Memory: 일별 피크 8일 (기본값)
VPA 최적화된 requests
Auto Mode가 노드 정리 판단

Auto Mode

  • Pod requests 합계로 노드 선택
  • NodePool 조건 안에서 인스턴스 매칭
  • requests가 줄면 노드에 빈자리 발생
  • Consolidation이 삭제 또는 교체 판단
⚙

VPA

Pod의 CPU/Memory requests를 사용량에 맞게 조정

⚡

Auto Mode

줄어든 requests로 빈 노드를 정리 (EKS 1.37 신규 풀은 Balanced 기본)

✔

주의

같은 CPU/Memory 메트릭으로 HPA와 함께 쓰지 않기

VPA 모드 비교

updateMode별 동작 방식과 권장 사용 사례

Off 모드

추천값만 제공하고, Pod를 변경하지 않습니다. 가장 안전한 분석 모드입니다.

장점

Pod 재시작 없음, 안전하게 분석 가능, 프로덕션에서 먼저 테스트

단점

자동 적용되지 않음, 수동 업데이트 필요

권장 사용 사례

신규 워크로드 분석, 프로덕션 사전 검증, 리소스 패턴 파악

YAMLapiVersion: autoscaling.k8s.io/v1 kind: VerticalPodAutoscaler metadata: name: my-app-vpa spec: targetRef: apiVersion: apps/v1 kind: Deployment name: my-app updatePolicy: updateMode: "Off"

Initial 모드

Pod 생성 시에만 추천값을 적용하고, 실행 중인 Pod는 변경하지 않습니다.

장점

실행 중 Pod 안정성 보장, 롤링 업데이트 시 자연스럽게 적용

단점

즉시 적용되지 않음, 새 Pod 생성까지 대기 필요

권장 사용 사례

Stateful 워크로드, 긴 실행 배치 작업, 재시작에 민감한 서비스

YAMLapiVersion: autoscaling.k8s.io/v1 kind: VerticalPodAutoscaler metadata: name: my-app-vpa spec: targetRef: apiVersion: apps/v1 kind: Deployment name: my-app updatePolicy: updateMode: "Initial"

Recreate 모드

추천값과 차이가 크면 Updater가 Pod를 evict하고, Admission Controller가 새 Pod에 추천값을 넣습니다. VPA 1.5부터 기본 모드입니다.

장점

모든 Kubernetes 버전에서 동작, 동작이 예측 가능

단점

Pod 재시작 발생, PDB와 레플리카 2개 이상 필요

권장 사용 사례

Stateless 워크로드, 개발/스테이징 환경, 다중 레플리카 서비스

YAMLapiVersion: autoscaling.k8s.io/v1 kind: VerticalPodAutoscaler metadata: name: my-app-vpa spec: targetRef: apiVersion: apps/v1 kind: Deployment name: my-app updatePolicy: updateMode: "Recreate"

InPlaceOrRecreate 모드 (VPA 1.6 GA)

Pod를 재시작하지 않고 resize subresource로 requests를 바꿉니다. 노드에 자리가 없는 등 in-place가 불가능하면 evict로 전환합니다.

장점

재시작 없이 조정, Kubernetes 1.35부터 in-place resize GA

단점

QoS class는 바꿀 수 없음, 노드 여유가 없으면 결국 evict

권장 사용 사례

재시작 비용이 큰 서비스, EKS 1.35 이상 클러스터. evict 없는 InPlace 모드는 VPA 1.8에서도 alpha

YAMLapiVersion: autoscaling.k8s.io/v1 kind: VerticalPodAutoscaler metadata: name: my-app-vpa spec: targetRef: apiVersion: apps/v1 kind: Deployment name: my-app updatePolicy: updateMode: "InPlaceOrRecreate"

Auto 모드

VPA 1.5부터 deprecated이며 현재 Recreate와 같게 동작합니다. 향후 API 버전에서 제거될 예정이므로 Recreate 또는 InPlaceOrRecreate를 명시합니다.

장점

기존 매니페스트와 호환

단점

Deprecated, 의미가 바뀔 수 있음, Pod 재시작 발생

권장 사용 사례

신규 설정에는 사용하지 않음. 기존 Auto 설정은 명시적 모드로 전환

YAMLapiVersion: autoscaling.k8s.io/v1 kind: VerticalPodAutoscaler metadata: name: my-app-vpa spec: targetRef: apiVersion: apps/v1 kind: Deployment name: my-app updatePolicy: updateMode: "Auto"

빈 노드 삭제 또는 더 저렴한 노드로 교체

📊 리소스 모니터링

# Recommender 기본값 (VPA 1.8) CPU: decaying histogram, 반감기 24h Memory: 24h 피크 × 8개 구간 (8일) # 예시 관측값 CPU P90: 260m / 요청: 500m Memory P90: 445Mi / 요청: 1Gi

💡 추천값 생성

# target = P90 × (1 + 0.15) Recommendation: Container: my-app Lower Bound: CPU: 200m, Mem: 350Mi Target: CPU: 300m, Mem: 512Mi ← 권장 Upper Bound: CPU: 450m, Mem: 700Mi Uncapped: CPU: 300m, Mem: 512Mi

→ requests 기준 CPU 40%, Memory 50% 감소 (예시)

🔄 Pod Requests 업데이트

# InPlaceOrRecreate: resize 시도, 실패 시 evict resources: requests: cpu: 500m → 300m # -40% memory: 1Gi → 512Mi # -50% limits: cpu: 1000m → 600m memory: 2Gi → 1Gi # limits는 기존 request:limit 비율 유지

🔍 노드에 빈자리 발생

# 노드는 바로 바뀌지 않음 Nodes: 3x c6g.large (6 vCPU, 12Gi) requests 합계: 감소 → 노드마다 빈자리 # 직접 설치 Karpenter v1.14+: spec과 # status.allocatedResources 중 큰 값으로 계산

📦 Consolidation 판단

# Pod를 옮길 수 있으면 검토 삭제: 남은 노드에 Pod가 모두 들어가면 1대 제거 교체: 더 저렴한 노드 1대로 바꿀 수 있으면 교체 # Balanced: 절감액 대비 Pod 중단 비용 평가 # PDB, Disruption Budget, do-not-disrupt 존중

📏 결과 확인

# 예시: us-east-1 On-Demand 가격 가정 Before: 3x c6g.large ($0.068/h) = $0.204/h After: 2x c6g.large = $0.136/h 절감: $0.068/h (약 33%, 월 ~$50) # 함께 볼 지표: Pod 재시작, Pending, 지연

→ 실제 절감률은 워크로드와 NodePool 조건에 따라 다릅니다

Production Best Practices

  • CPU: request만 설정, limit 없음 - Burstable로 CPU throttling 방지
  • Memory: request == limit, 다른 Pod의 메모리 압박으로 인한 eviction 위험 감소
  • 권장 패턴: CPU request only + Memory request == limit (Pod QoS는 Burstable)
Recommended Patternresources: requests: cpu: "500m" # CPU request only memory: "512Mi" # Memory request == limit limits: # cpu: (no limit) # Allows bursting memory: "512Mi" # Same as request
현재 설정: CPU request만, Memory request == limit: 권장 패턴입니다 (Pod QoS는 Burstable).

HPA: Horizontal Pod Autoscaler

CPU, Memory, Custom Metrics 기반 수평 확장

# HorizontalPodAutoscaler (autoscaling/v2) spec: scaleTargetRef: { name: my-app } minReplicas: 2 / maxReplicas: 20 metrics: - type: Resource resource: name: cpu target: type: Utilization averageUtilization: 70 # CPU 70% - type: Resource resource: name: memory target: type: Utilization averageUtilization: 80 # Memory 80% behavior: scaleDown: { stabilizationWindowSeconds: 300 } scaleUp: { stabilizationWindowSeconds: 30 }
# Prometheus Adapter 설치 필요 # helm install prometheus-adapter prometheus-community/prometheus-adapter apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: name: my-app-rps-hpa spec: scaleTargetRef: apiVersion: apps/v1 kind: Deployment name: my-app minReplicas: 2 maxReplicas: 20 metrics: - type: Pods pods: metric: name: http_requests_per_second target: type: AverageValue averageValue: 100 # Pod당 100 RPS - type: External external: metric: name: sqs_queue_length target: type: AverageValue averageValue: 50

HPA 한계점

  • minReplicas ≥ 1: 기본적으로 Scale-to-Zero 불가 (HPAScaleToZero는 alpha feature gate)
  • Custom Metrics: Prometheus Adapter 별도 설치, 관리 필요
  • AWS 통합: SQS, MSK 등은 External metrics adapter 별도 필요
  • PromQL 직접 사용 불가: Adapter 규칙으로 변환해야 해서 복잡도 증가
  • 대상당 HPA 1개: 같은 Deployment에 HPA를 여러 개 두면 서로 충돌 (KEDA는 ScaledObject 하나에 trigger 여러 개)
KEDA가 해결하는 것: HPA를 직접 생성, 관리하면서 70개 이상의 스케일러를 지원하고 Scale-to-Zero까지 가능하게 합니다.

AWS 메트릭 기반 스케일링

SQS Queue Depth / MSK Consumer Lag / ALB Request Count

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: sqs-consumer-scaler
spec:
  scaleTargetRef:
    name: sqs-consumer
  minReplicaCount: 0  # Scale-to-Zero!
  maxReplicaCount: 20
  triggers:
  - type: aws-sqs-queue
    authenticationRef:
      name: keda-aws-credentials
    metadata:
      queueURL: https://sqs.ap-northeast-2...
      queueLength: "5"  # 메시지 5개당 1 Pod
      awsRegion: ap-northeast-2

🎯 SQS 네이티브 스케일러

  • aws-sqs-queue: Prometheus 불필요
  • queueLength: "5": 메시지 5개당 Pod 1개
  • Scale-to-Zero: 큐 비어있으면 Pod 0
  • IRSA 기반 인증 (TriggerAuthentication, podIdentity.provider: aws)
💡 IRSA 설정 필수: TriggerAuthentication의 podIdentity.provider: aws로 SQS 조회 권한 부여. aws-eks는 deprecated

Best Practices 체크리스트

리소스 최적화를 위한 운영 가이드

VPA 설정

  • VPA를 Off 모드로 먼저 분석 (메모리 기본 창 8일 이상)
  • 핵심 워크로드부터 VPA 적용
  • CPU는 request만, Memory는 request=limit
  • 적용은 Recreate 또는 InPlaceOrRecreate 명시 (Auto 사용 안 함)

NodePool 전략

  • NodePool 분리: 웹/배치/GPU
  • Graviton 인스턴스 허용 (arm64)
  • Spot 혼합 전략 (Stateless 워크로드)
  • Pod Priority로 중요 워크로드 보호

KEDA 스케일링

  • TriggerAuthentication podIdentity.provider: aws 구성
  • cooldownPeriod로 스케일링 진동 방지
  • fallback 설정으로 메트릭 장애 대비
  • CPU/Memory는 VPA와 HPA 중 하나만 사용

비용 & 모니터링

  • 정기적 비용 리뷰 (월 1회)
  • Cost Allocation Tags 적용
  • VPA 추천값 대시보드 구성
  • 노드 활용률 알림 설정

전체 과정 요약

Key Takeaways

BLOCK 01

EKS Auto Mode 내부 아키텍처

Auto Mode는 AWS가 관리하는 Karpenter 기반 노드 관리. NodePool과 NodeClass로 제어하고, 직접 설치한 Karpenter(v1.15.0)와 API와 운영 책임이 다릅니다.

BLOCK 02

노드 라이프사이클 모니터링

Pod, 노드, 이벤트 순서로 진단. Spot 회수 대응, expireAfter와 Disruption Budget으로 Day-2 운영 안정화.

BLOCK 03

3-Signal Correlation

Exemplars, Derived Fields, tracesToLogsV2로 Logs, Metrics, Traces 상관분석. 근본 원인 분석 가속화.

BLOCK 04

VPA + KEDA + Auto Mode 최적화

VPA(InPlaceOrRecreate)로 requests 조정, KEDA로 이벤트 기반 스케일링, Auto Mode Consolidation으로 빈 노드 정리.
