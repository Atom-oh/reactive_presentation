Built-in 풀과 default NodeClass

NodePool아키텍처용량, 인스턴스누가 올라가나

수정하지 말고 추가
built-in 풀은 AWS 관리 객체입니다. Spot, Graviton 범용, GPU는 커스텀 NodePool로 만듭니다. 1.37에서 built-in 풀은 Balanced입니다.
default NodeClass 조건
built-in 풀이 하나 이상 켜져 있어야 생깁니다. 둘 다 끄면 NodeClass를 직접 만들고 참조를 바꿉니다.
목록에서 빼면 노드 종료

추측 말고 조회: kubectl get nodepool general-purpose system -o yaml, kubectl get nodeclass default -o yaml로 실제 disruption과 taint 값을 확인합니다.

커스텀 NodeClass: 필드 지도

apiVersion: eks.amazonaws.com/v1
kind: NodeClass
spec:
  role: AmazonEKSAutoNodeRole  # 또는 instanceProfile
  subnetSelectorTerms:
  - tags: {kubernetes.io/role/internal-elb: "1"}
  securityGroupSelectorTerms:
  - tags: {Type: worker-node}
  ephemeralStorage:
    size: 100Gi
    iops: 3000
    throughput: 125
  advancedNetworking:
    associatePublicIPAddress: false
  advancedCompute:
    kernel:
      sysctl: {vm.max_map_count: 262144}
  tags: {Environment: production}
role과 instanceProfile은 하나만
AmazonEKSComputePolicy가 eks* 이름의 instance profile에만 권한을 주므로 이름을 eks로 시작합니다. 새 역할에는 access entry가 필요합니다.
tags는 클러스터 역할 권한 필요
커스텀 태그 키로 리소스를 만들 권한이 없으면 launch가 실패합니다. 데모에서 CreateLaunchTemplate 권한 오류로 확인했습니다.
sysctl 변경은 Drift
부팅 시 적용되므로 기존 노드는 교체됩니다. 실행 중인 노드에 바로 적용되지 않습니다.
필드하는 일주의
ephemeralStorage.kmsKeyID노드 root, data EBS를 고객 관리 키로 암호화같은 리전 키. NVMe instance store와 앱 PVC에는 적용 안 됨
certificateBundles[].data사설 CA를 노드 신뢰 저장소에 추가 (base64)앱 컨테이너의 trust store는 바뀌지 않음
podSubnetSelectorTermsPod IP를 노드와 다른 subnet에서 할당podSecurityGroupSelectorTerms와 반드시 함께. namespace 단위가 아니라 NodeClass 단위
podSecurityGroupSelectorTermsPod 네트워크에 붙일 security group
advancedNetworking.associatePublicIPAddressfalse면 노드에 공인 IP 없음outbound 경로(NAT, endpoint)는 따로 필요
EC2NodeClass에서 옮기면 안 되는 필드
amiFamily, amiSelectorTerms, blockDeviceMappings, userData, metadataOptions. OS는 AWS가 고르는 Bottlerocket 변형입니다.
대체 경로
디스크는 ephemeralStorage, 부팅 sysctl은 advancedCompute.kernel.sysctl, IMDS는 고정값(다음 장)

바꿀 수 없는 보안 기본값

IMDSv2, hop limit 1 고정
일반 Pod는 노드 메타데이터에 닿지 못합니다. hostNetwork Pod는 예외이니 앱 권한은 Pod Identity로 주고 리전 같은 값은 명시합니다.
SSH, SSM 접속 없음
관리형 Bottlerocket 변형, 읽기 전용 root 파일 시스템, SELinux enforcing. 노드에 들어가 고치는 운영은 불가
노드 역할은 최소 권한
WorkerNodeMinimalPolicy와 ContainerRegistryPullOnly. 앱 권한을 노드 역할에 넣지 않습니다.
최대 21일, 주간 AMI
패치는 새 AMI와 Drift로 들어옵니다. 오래된 노드가 남지 않는 대신 교체를 견디는 앱이 전제입니다.
taint와 label은 보안 경계가 아님: 배치를 나누는 도구입니다. 테넌트 격리가 필요하면 클러스터, 계정, 네트워크 정책 수준에서 나눕니다.

Spot, 예약 용량, 정적 풀

커스텀 풀이 필요
built-in 풀은 On-Demand만. 한 풀 안의 우선순위는 reserved, spot, on-demand이고, 배열 순서와 weight는 Spot 비율을 정하지 않습니다.
selector가 reserved를 뺄 수 있음
Pod의 capacity-type: on-demand nodeSelector는 예약 용량을 제외합니다. preferred affinity는 비율을 보장하지 않습니다.
NTH는 필요 없음
중단 처리는 내장입니다. Node Termination Handler DaemonSet과 SQS를 Auto Mode 노드에 두면 처리가 중복됩니다.
2분은 best effort
감지, eviction, 종료 처리가 시간을 씁니다. preStop: sleep 90은 예산 대부분을 소비하는 안티패턴입니다.
# NodeClass
spec:
  capacityReservationSelectorTerms:
  - id: cr-0123456789abcdef0
# NodePool
requirements:
- key: karpenter.sh/capacity-type
  operator: In
  values: ["reserved"]
기존 예약을 고르는 것
manifest가 예약을 만들지 않습니다. 계정, AZ, 유형, 남은 수량을 먼저 확인합니다.
켜면 클러스터 전체가 바뀜
한 NodeClass라도 capacityReservationSelectorTerms를 쓰면 클러스터의 모든 NodeClass가 open ODCR 자동 사용을 멈춥니다. 예약은 쓰지 않아도 과금됩니다.

미리 띄워 두는 노드
GPU 초기화나 cache warm-up처럼 기다릴 수 없는 워크로드용입니다.
동적 풀과 다른 규칙
limits는 nodes만, weight 설정 불가, consolidation 없음. replicas는 지울 수 없어 동적 풀로 되돌릴 수 없습니다.

1.37 업그레이드: Karpenter가 먼저

1Karpenter 1.15.xkarpenter-crd와 controller chart를 함께, 버전 문자열은 1.15.0
2상태 확인EC2NodeClass ValidationSucceeded, 대시보드 label 변경
3컨트롤 플레인 1.37리전 기본은 1.36이라 버전 명시
4노드 AMI 갱신alias pin을 1.37 AMI로 바꾸면 Drift로 롤링, budget 적용
왜 Karpenter가 먼저인가: 1.37 호환 버전은 1.15.x뿐입니다. v1.14 LTS로는 1.36까지만 갈 수 있습니다.
Node Repair가 voluntary로
대체 노드 선 생성, NDB reason UnhealthyⓘNDB = NodePool Disruption Budget (spec.disruption.budgets)
  • v1.15부터 graceful: 대체 노드를 먼저 띄운 뒤 PDB를 따라 drain (조건별 grace period가 상한)
  • reason Unhealthy: reasons: [Unhealthy]로 repair 속도만 제한. reasons 없는 budget(기본 10%)도 적용
  • NotReady를 빼지 않음: 고장 노드가 허용량을 다 써서 repair를 막지 않게 계산
  • 연쇄 고장 차단: 풀의 20% 넘게 고장이면 중단, NodeRepairBlocked 이벤트
  • CRD 먼저: enum에 Unhealthy가 추가되어 karpenter-crd를 같이 올려야 함
  • 켜기: self-managed는 NodeRepair gate (alpha, 기본 off), Auto Mode는 내장
. CRD enum이 바뀌므로 CRD를 함께 업그레이드
ⓘ에 마우스를 올리면 설명
kubelet 검증이 controller로

reason 소문자화, consolidation_type은 empty, single, multi, 미분류 error는 unknown
1관리형 구성 요소Karpenter, CNI, CoreDNS 등은 AWS가 업데이트

PVC는 넘어오지 않음
다른 provisioner의 볼륨은 마운트할 수 없습니다. snapshot 복원이나 Retain 후 static PV 재생성, AWS의 migration tool을 씁니다.
LB도 인수하지 않음
새 LB를 만들고 DNS로 blue/green 전환합니다. 기존 LB controller는 자기 리소스가 남아 있는 동안 유지합니다.
CoreDNS Deployment 유지
Auto Mode 노드는 node-local DNS를 씁니다. Auto가 아닌 노드가 남아 있는 동안 기존 CoreDNS를 지우지 않습니다.

Auto Mode인가, 직접 운영인가

직접 운영 쪽 신호

  • custom AMI, userData, launch template, SSH나 SSM 접속이 필요
  • kubelet, sysctl 요구가 advancedCompute 지원 필드를 벗어남
  • Windows 노드, DRA, 대체 CNI 필요 (Security Groups per Pod는 podSecurityGroupSelectorTerms로 대체)
  • feature gate 기능이나 FIS EC2 장애 주입 테스트가 필요

Auto Mode 쪽 신호

  • Karpenter minor마다 CRD와 breaking change를 따라갈 인력이 부족
  • CNI, CoreDNS, EBS CSI, LB controller 운영을 줄이고 싶음
  • 주간 AMI 교체와 21일 수명 상한을 보안 기준으로 받아들일 수 있음
  • 인스턴스당 관리비가 운영 시간 절감보다 작다고 판단
