온프렘 K8s, 왜 아직도 힘든가

컨트롤 플레인 직접 운영
etcd 백업·복구, API server 가용성, 인증서 갱신을 팀이 직접 책임
버전 업그레이드 부담
마이너 버전마다 컨트롤 플레인과 노드를 순서대로 올려야 하고, 실패 시 영향 범위가 큼
클러스터 파편화
클라우드와 온프렘이 서로 다른 도구·정책·버전으로 따로 운영되기 쉬움
인증·감사 이원화
IAM 기반 클라우드 권한 체계와 온프렘 인증 체계를 각각 관리
GPU·데이터 근접성
기존 하드웨어와 대규모 로컬 데이터 때문에 워크로드를 클라우드로 옮기기 어려움
가시성 도구 분산
모니터링·로깅이 환경별로 나뉘어 한 화면에서 보기 어려움

Edge 옵션, 책임 경계가 다르다

옵션컨트롤 플레인워커 노드인프라 소유
EKS (클라우드)AWS 관리AWS Region의 컴퓨팅AWS
EKS on Local ZonesAWS 관리 (Region)Local Zone의 AWS 인프라AWS
EKS on Outposts확장 클러스터는 Region, 로컬 클러스터는 Outposts에서 AWS 관리고객 시설에 설치된 AWS 인프라AWS 제공
EKS Anywhere고객이 직접 운영고객 인프라고객
EKS Hybrid NodesAWS 관리 (EKS)고객 소유 온프레미스·엣지 호스트고객
Local Zone·Outposts·다른 클라우드의 머신을 hybrid node 인프라로 등록하는 것은 지원하지 않습니다. 이 비교는 개념 수준이며, 상세 지원 범위는 각 서비스의 공식 문서로 확인하세요.

컨트롤 플레인만 AWS에 맡긴다

What
온프레미스·엣지 노드를 AWS 관리형 EKS 컨트롤 플레인에 연결하는 기능
Why
클라우드와 온프렘을 같은 EKS API, 같은 도구로 운영하고 컨트롤 플레인 운영 부담을 줄임
단, 책임은 남는다
Host·OS·연결·워크로드 운영은 계속 고객 몫

Ready까지 여섯 단계

1nodeadm install · init
의존성 설치와 구성. nodeadm은 상시 에이전트가 아닌 설치/bootstrap/upgrade CLI
2자격 증명 획득
SSM 또는 IAM Roles Anywhere로 임시 자격 증명 확보 (AWS 연결 필요)
3kubelet 기동
label eks.amazonaws.com/compute-type=hybrid 자동 부여, taint는 자동 아님
4EKS API 인증
Node IAM role의 HYBRID_LINUX access entry로 system:node 신원 매핑
5CNI 설치
Cilium 또는 Calico 필요. VPC CNI는 hybrid node를 관리하지 않음
6Ready
Pod 스케줄 가능. Pod Identity 등 add-on은 별도 구성

책임은 나뉘고, 데이터는 AWS에

AWS 책임
  • EKS API server, etcd, scheduler, controller
  • SSM / IAM Roles Anywhere 서비스
  • 컨트롤 플레인 가용성 관리
고객 책임
  • Host, OS, 보안 패치, kubelet·containerd 운영
  • CNI 구성, VPN·Direct Connect·라우팅
  • 노드 인증서·자격 증명 준비, 워크로드 운영
데이터 경계 주의 — Secrets, Kubernetes 객체, 로그 등 컨트롤 플레인 데이터는 AWS에 저장됩니다. Private endpoint를 쓴다고 망분리 규정 준수가 입증되지는 않으며, Direct Connect 자체는 기본 암호화를 제공하지 않습니다.

도입 전 꼭 확인할 6가지 제약

IPv4 전용
Remote node·Pod CIDR은 RFC1918 또는 CGNAT(100.64.0.0/10)이며 VPC·service CIDR과 겹치면 안 됨
CIDR 개수 상한
클러스터당 remote node CIDR 15개, remote Pod CIDR 15개까지. 기존 클러스터에도 추가 가능
연결형 환경 전제
AWS와 안정적인 private 양방향 연결 필요. 단절·간헐 연결(DDIL) 용도 아님
권장 연결 품질
일반 권장: 100 Mbps 이상, RTT 200 ms 이하 (엄격한 최소값은 아님)
API endpoint는 하나만 권장
Public-only 또는 Private-only 권장. "Public and Private"는 VPC 밖 노드에서 endpoint가 public IP로 해석되어 join이 실패할 수 있음
노드는 유휴여도 과금
Join부터 제거까지 vCPU-hour로 과금. Workload가 idle이어도 자동 중단되지 않음

Join 전 사전 준비 체크리스트

  • Access entry: node IAM role에 HYBRID_LINUX 타입 생성
    { "clusterName": "my-hybrid-cluster", "principalArn": "arn:aws:iam::123456789012:role/EKSHybridNodeRole", "type": "HYBRID_LINUX" }
  • remoteNetworkConfig: remote node·Pod CIDR 선언 (기존 클러스터에도 추가 가능)
    remoteNetworkConfig: remoteNodeNetworks: - cidrs: [10.80.0.0/16] remotePodNetworks: - cidrs: [10.85.0.0/16]
  • IAM: eks:DescribeCluster 포함 (AmazonEKSWorkerNodeMinimalPolicy에는 없음)
  • CIDR: IPv4, RFC1918/CGNAT, VPC·service CIDR과 중복 없음
  • 연결: TGW/VGW 양방향 라우팅, 443 / 10250 / webhook 포트 방화벽
  • OS: 지원 OS·nodeadm 버전·containerd source 확인
