비교 1: 신뢰와 연결을 거는 위치

IRSA
클러스터 준비: 클러스터마다 IAM OIDC provider 등록
연결 위치: Kubernetes ServiceAccount 주석

Pod Identity
클러스터 준비: 클러스터마다 Agent 애드온 (Auto Mode는 내장)
연결 위치: EKS API association, Kubernetes 객체 변경 없음
aws eks create-pod-identity-association --namespace wid-<run> --service-account orders-podid --role-arn ...
IRSA: Federated + aud, sub 
{
  "Effect": "Allow",
  "Principal": {"Federated":
    "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/<OIDC_ISSUER>"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {"StringEquals": {
    "<OIDC_ISSUER>:aud": "sts.amazonaws.com",
    "<OIDC_ISSUER>:sub":
      "system:serviceaccount:<NAMESPACE>:<IRSA_SA>"
  }}
}
클러스터가 늘 때마다 이 문장을 추가합니다.
Pod Identity: 서비스 principal 하나 
{
  "Effect": "Allow",
  "Principal": {"Service": "pods.eks.amazonaws.com"},
  "Action": ["sts:AssumeRole", "sts:TagSession"],
  "Condition": {"StringEquals": {
    "aws:RequestTag/eks-cluster-arn": "<CLUSTER_ARN>",
    "aws:RequestTag/kubernetes-namespace": "<NAMESPACE>",
    "aws:RequestTag/kubernetes-service-account":
      "<POD_IDENTITY_SA>"
  }}
}
조건은 선택입니다. 쓰려면 association의 세션 태그를 켠 상태로 둡니다.

장단점: IRSA와 Pod Identity

IRSA

장점

  • Fargate, Windows, EKS 밖(EKS Anywhere, ROSA, 자체 관리)에서도 같은 방식
  • 애드온 없이 IAM OIDC provider와 STS만으로 동작
  • 교차 계정: 대상 계정 역할이 이 클러스터의 provider를 직접 신뢰

단점

  • 클러스터마다 OIDC provider 등록 (계정당 기본 100개)
  • 새 클러스터마다 신뢰 정책 수정, 기본 2,048자라 역할당 보통 4개 안팎
  • 세션 태그 없음, Pod가 STS를 직접 호출해 STS 할당량 사용
Pod Identity

장점

  • 신뢰 정책은 서비스 principal 하나, 클러스터가 늘어도 그대로
  • 세션 태그로 ABAC: 한 역할을 여러 ServiceAccount에
  • 연결은 EKS API, 권한은 IAM: 팀 간 책임 분리

단점

  • Agent 애드온과 노드 역할의 eks-auth:AssumeRoleForPodIdentity 필요 (Auto Mode는 내장)
  • EKS Linux EC2와 Hybrid Nodes만: Fargate, Windows는 지원하지 않음
  • 지원 SDK 최소 버전 확인, 교차 계정은 대상 역할 지정이나 체이닝
출처: Amazon EKS User Guide, Comparing EKS Pod Identity and IRSA, Learn how EKS Pod Identity grants pods access

옮기면 얻는 것: 보안과 운영 비용

보안 (두 방식 공통)
  • 권한 범위가 노드에서 ServiceAccount로: 그 SA를 쓰는 Pod만 권한을 받음
  • 노드 역할 회수와 IMDS 차단 뒤에는 다른 Pod의 역할에 닿지 않음
  • CloudTrail에 워크로드 역할 세션으로 남아 추적과 회수 범위가 좁아짐
  • 임시 자격 증명과 자동 갱신은 그대로, 단위만 노드에서 워크로드로

운영 이전은 다섯 단계, 회수는 맨 뒤

  1. 의존성 조사
    노드 역할 정책과 CloudTrail의 실제 세션 비교. 워커 노드, ECR pull 권한은 유지
  2. 역할과 전용 SA 준비
    리소스 단위로 제한한 워크로드 역할. SDK 최소 버전 확인
  3. 카나리 Pod 새로 생성
    주입된 env 이름, 호출자 ARN, API 성공 확인. 토큰과 키는 로그에 출력하지 않기
  4. 순차 전환 후 회수
    AccessDenied, 갱신, 크론까지 관찰. 노드 역할의 해당 정책 문장만 회수
  5. 노드 접근 제한
    IMDSv2 강제, hop limit 1. hostNetwork Pod는 별도 통제

IRSA로 옮기기: provider, 역할, 주석

준비 (클러스터와 역할마다)
1

클러스터의 IAM OIDC provider 등록

eksctl utils associate-iam-oidc-provider \
  --cluster $CLUSTER --approve
2

역할: Federated 신뢰 + aud, sub 조건

aws iam create-role --role-name orders-irsa \
  --assume-role-policy-document file://trust-irsa.json
aws iam put-role-policy --role-name orders-irsa \
  --policy-name orders-s3 --policy-document file://orders-s3.json
신뢰 정책 JSON은 1부 비교 1. 새 클러스터에서 쓰려면 1과 신뢰 정책 문장을 다시 추가합니다.
워크로드마다
3

ServiceAccount에 주석

kubectl -n orders annotate serviceaccount orders \
  eks.amazonaws.com/role-arn=arn:aws:iam::<ACCOUNT_ID>:role/orders-irsa
4

Pod 재생성과 확인

kubectl -n orders rollout restart deployment/orders
# 카나리 Pod: AWS_ROLE_ARN 주입, 호출자 ARN이 assumed-role/orders-irsa
5

노드 역할에서 그 앱의 정책 문장만 회수

줄여 쓰기: eksctl create iamserviceaccount가 2와 3을 한 번에 합니다(이미 있는 SA는 --override-existing-serviceaccounts). 이미 떠 있는 Pod에는 주입되지 않으니 4의 재생성이 꼭 필요합니다.

Pod Identity로 옮기기: Agent와 연결

준비 (클러스터마다 한 번, 역할은 재사용)
1

Agent 애드온 (Auto Mode는 생략)

aws eks create-addon --cluster-name $CLUSTER \
  --addon-name eks-pod-identity-agent
노드 역할에 eks-auth:AssumeRoleForPodIdentity (AmazonEKSWorkerNodePolicy에 포함)
2

역할: 서비스 principal 신뢰

aws iam create-role --role-name orders-podid \
  --assume-role-policy-document file://trust-podid.json
aws iam put-role-policy --role-name orders-podid \
  --policy-name orders-s3 --policy-document file://orders-s3.json
# 신뢰: pods.eks.amazonaws.com, sts:AssumeRole + sts:TagSession
워크로드마다
3

association 생성 (Kubernetes 객체 변경 없음)

aws eks create-pod-identity-association \
  --cluster-name $CLUSTER --namespace orders \
  --service-account orders \
  --role-arn arn:aws:iam::<ACCOUNT_ID>:role/orders-podid
4

Pod 재생성과 확인

kubectl -n orders rollout restart deployment/orders
# AWS_CONTAINER_CREDENTIALS_FULL_URI 주입, 호출자 ARN 확인
5

노드 역할에서 그 앱의 정책 문장만 회수

IRSA에서 옮길 때: 신뢰 정책에 서비스 principal 추가, association, rollout, 확인 뒤 OIDC 신뢰와 SA 주석 정리. eksctl utils migrate-to-pod-identity --cluster $CLUSTER는 Agent, 신뢰 정책, association을 클러스터 전체에 일괄 처리합니다. --approve 없이 실행하면 계획만 출력합니다.

교차 계정: IRSA와 Pod Identity

A 계정 클러스터의 Pod가 B 계정 리소스로IRSAPod Identity (대상 역할)
B 계정에서 할 일A 클러스터의 OIDC issuer를 B 계정 IAM provider로 등록, B 역할에 Federated 신뢰와 sub, aud 조건B 역할이 A 역할을 신뢰, External ID 조건 권장
클러스터가 늘면B 계정마다 provider 등록과 신뢰 정책 수정. 클러스터 수 × 계정 수만큼 providerB 쪽은 그대로, A 쪽에 association만 추가
역할 홉Pod가 B 역할을 바로 맡음 (1홉)A 역할을 거쳐 B 역할로, EKS가 대신 체이닝
앱 변경없음, SA 주석에 B 역할 ARN없음, association에 두 역할
 
aws eks create-pod-identity-association \
  --cluster-name $CLUSTER --namespace orders --service-account orders \
  --role-arn        arn:aws:iam::<ACCOUNT_A>:role/account-a-role \
  --target-role-arn arn:aws:iam::<ACCOUNT_B>:role/account-b-role
External ID EKS가 리전/A계정/클러스터/namespace/SA로 자동으로 넣습니다. B 역할 신뢰 정책의 sts:ExternalId 조건에 이 값을 겁니다.
출처: AWS Containers Blog, EKS Pod Identity streamlines cross account access, EKS Best Practices, Multi Account Strategy

주석이 남아도 새 Pod는 Pod Identity

IRSA에서 Pod Identity로 옮기는 도중

ServiceAccount orders   # role-arn 주석이 남아 있음
association    orders   ...:role/new-podid

# 새 Pod: EKS 웹훅이 Pod Identity 변수만 주입
AWS_CONTAINER_CREDENTIALS_FULL_URI
AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE
# association 전에 만든 Pod: IRSA 변수 유지
AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE
결정은 SDK 체인이 아니라 주입 단계에서 납니다. 기존 Pod는 재생성 전까지 IRSA입니다.
체인 순서와 헷갈리지 않기: 체인에서는 웹 ID 토큰이 앞이지만, EKS는 한 Pod에 두 변수 세트를 함께 넣지 않습니다.

노드 역할 두 길에 모두 나옵니다. access entry(EC2_LINUX, Hybrid Nodes는 HYBRID_LINUX)로 노드가 클러스터에 가입하고, 같은 역할로 Pod Identity Agent가 EKS Auth를 부릅니다. 그래서 이전 마지막에 지우는 것은 앱 권한뿐이고, 노드 역할과 access entry는 그대로 둡니다.
출처: Amazon EKS User Guide, Grant IAM users and roles access to Kubernetes APIs, Create access entries, Migrating aws-auth entries to access entries, EKS Best Practices, Identity and Access Management

kubeconfig의 exec 설정이 요청 때 aws eks get-token을 불러 토큰을 받습니다. 토큰은 k8s-aws-v1. 뒤에 STS GetCallerIdentity presigned URL을 base64로 붙인 값입니다. control plane의 AWS IAM Authenticator for Kubernetes가 이 URL로 STS에 호출자를 확인하고, 그 IAM ARN을 access entry(또는 aws-auth ConfigMap)로 Kubernetes 사용자와 그룹에 매핑합니다.

같은 IAM 역할이 양쪽에 매핑되어 있으면 access entry가 우선합니다. kubectl에서 Unauthorized가 나오면 Pod 자격 증명이 아니라 이 매핑을 먼저 봅니다.

Pod의 자격 증명은 세 곳에서 온다

같은 노드의 orders 앱 세 벌이 서로 다른 곳에서 임시 자격 증명을 받고, 결국 같은 방식으로 S3 요청에 서명한다.

  1. 노드 역할: 주입된 변수가 없는 Pod는 IMDSv2에서 노드 역할을 받는다
  2. IRSA(IAM Roles for Service Accounts): Pod가 projected 토큰으로 리전 STS(Security Token Service) AssumeRoleWithWebIdentity를 호출한다
  3. Pod Identity (1): Pod는 같은 노드의 Pod Identity Agent에만 묻는다
  4. Pod Identity (2): Agent가 EKS Auth AssumeRoleForPodIdentity를 호출해 받아 온다
  5. 결과: 세 Pod 모두 받은 임시 자격 증명으로 S3 요청에 서명한다

CREATE에서만 동작: 실행 중인 Pod는 바뀌지 않습니다. 설정 뒤에는 rollout.
failurePolicy: Ignore: 웹훅이 응답하지 못하면 변수 없이 Pod가 만들어져 조용히 노드 역할로 동작합니다. 그래서 호출자 ARN으로 확인합니다.
미리 확인: kubectl create --dry-run=server로 Pod 템플릿을 보내면 웹훅을 거친 결과를 Pod를 만들지 않고 볼 수 있습니다.

IRSA: Pod가 토큰을 들고 STS로 간다

신뢰 준비
클러스터 issuer를 IAM OIDC(OpenID Connect) provider로 한 번 등록
주입
SA 주석을 본 EKS mutating webhook(amazon-eks-pod-identity-webhook)이 env와 토큰 볼륨 추가
교환
Pod가 리전 STS(Security Token Service)와 직접 통신
출처: Amazon EKS User Guide, IAM roles for service accounts

EKS 클러스터마다 OIDC issuer URL이 있습니다. 이 issuer를 계정의 IAM OIDC provider로 등록하면, IAM 역할의 신뢰 정책이 그 provider를 Federated principal로 지정할 수 있습니다. STS는 provider에 등록된 issuer의 공개 키로 Pod 토큰의 서명을 검증합니다. 클러스터를 새로 만들 때마다 provider 등록과 신뢰 정책 수정이 필요합니다.

Pod Identity: Agent가 대신 묻는다

연결
EKS API의 association, 주석 없음
조회
SDK는 같은 노드의 Agent만 호출
위임
EKS Auth가 역할을 맡고 세션 태그 부착
출처: Amazon EKS User Guide, How EKS Pod Identity works

aws eks create-pod-identity-association으로 만드는 EKS 리소스입니다. 클러스터, namespace, ServiceAccount 조합을 IAM 역할 하나에 연결합니다. Kubernetes 객체에는 주석을 달지 않으며, 클러스터당 association은 5,000개까지 만들 수 있습니다. 생성 직후 몇 초 동안은 새 Pod에 반영되지 않을 수 있습니다(eventual consistency).
