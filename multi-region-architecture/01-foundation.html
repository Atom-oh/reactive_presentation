리전 규모 장애 격리가용성
Multi-AZ는 AZ 장애를 막고, 멀티리전은 리전 전체에 영향을 주는 드문 이벤트를 막습니다
사용자 근접 지연성능
CDN이 못 줄이는 동적 API 읽기를 사용자와 가까운 리전에서 처리
데이터 레지던시규제
국가, 산업 규제로 특정 리전 안에 데이터를 보관해야 하는 경우
배포 blast radius 축소운영
한 리전씩 순차 배포하면 잘못된 변경의 영향 범위가 리전 하나로 제한
공짜가 아닙니다: 인프라 이중화, 리전 간 데이터 전송 요금, 일관성 설계, 페일오버 연습까지 비용이 늘어납니다. 목표 RTO, RPO가 이 비용을 정당화하는지 먼저 확인하세요.

Active-Active냐, Passive냐

Active-Active
  • 모든 리전이 동시에 트래픽 처리, 사용자는 가까운 리전으로
  • 리전 하나를 잃어도 다른 리전이 이미 서비스 중
  • 쓰기를 양쪽에서 받으면 충돌 해결 또는 동기 합의가 필요
  • 각 리전이 전체 부하를 흡수할 용량을 유지해야 함
Active-Passive
  • Primary만 트래픽 처리, secondary는 대기 또는 축소 운영
  • DR 전략 스펙트럼: Backup & Restore, Pilot Light, Warm Standby
  • 단방향 복제라 충돌이 없고 구현이 단순
  • 페일오버 절차와 승격 시간이 RTO를 결정
이 세션의 선택: 읽기는 Active-Active, 쓰기는 Active-Passive. 두 리전 모두 트래픽을 받되 쓰기는 us-east-1 한 곳으로 모읍니다 (Write-Primary / Read-Local).

일관성은 데이터마다 고른다

보장
어느 리전에서 읽어도 마지막으로 커밋된 쓰기가 보임
대가
쓰기, 강한 읽기 지연이 참여 리전 간 RTT에 비례
AWS 예
DynamoDB MRSC, Aurora DSQL multi-Region, Aurora write forwarding GLOBAL 모드
적합
결제 승인, 재고 차감처럼 중복이나 역전이 치명적인 데이터
보장
내 세션이 쓴 것은 내 세션에서 바로 보임 (read-your-writes)
대가
내 쓰기가 로컬로 복제될 때까지만 대기, 다른 세션의 변경은 늦게 보일 수 있음
AWS 예
apg_write_forward.consistency_mode 기본값 SESSION
적합
주문 직후 "내 주문 내역" 확인처럼 본인 데이터 확인 흐름
보장
충분한 시간이 지나면 모든 복제본이 같아짐, 그 전엔 stale 가능
대가
가장 빠르지만 앱이 stale 읽기와 충돌을 견뎌야 함
AWS 예
DynamoDB MREC, Aurora secondary 일반 읽기, EVENTUAL 모드, S3 복제
적합
상품 카탈로그, 리뷰, 추천, 검색 인덱스
payment
Strong: 쓰기는 primary writer에서만, 승인 결과는 primary 기준으로 확인
order
Session: secondary에서 write forwarding, 본인 주문은 바로 보이게
catalog
Eventual: 로컬 읽기, 가격, 재고 표시는 수 초 지연 허용
cart
Eventual + 캐시: 로컬 읽기, 장바구니 담기는 결제 직전에 primary로 재검증

리전마다 독립된 EKS 클러스터

클러스터는 리전 단위
EKS 컨트롤 플레인은 리전 서비스. 리전마다 독립 클러스터를 두고 서로 의존하지 않게 설계
버전을 맞춘다
두 리전 모두 같은 Kubernetes 버전. 2026-10 기준 최신은 1.37 (EKS 출시 2026-10-01)
GitOps로 같은 매니페스트
하나의 Git 저장소에서 두 클러스터로 배포, 리전 차이는 overlay 값(endpoint, ARN)으로만
이미지도 리전마다
ECR 리전 간 복제로 각 리전에서 로컬 pull. 다른 리전 레지스트리에 의존하지 않음
IAM은 Pod Identity
IAM role은 글로벌, association은 클러스터마다 생성. 리전별 리소스 ARN 범위 확인
흡수 용량 계획

리전 간 연결, 세 가지 선택지

언제
VPC 두세 개를 1:1로 붙일 때 가장 단순, 별도 hourly 요금 없음 (리전 간 전송 요금은 부과)
transitive 불가
A-B, A-C를 붙여도 B-C는 통신 불가. VPC가 늘면 n(n-1)/2 mesh
리전 간 SG 참조 불가
inter-Region peering에서는 상대 SG를 참조할 수 없어 CIDR 규칙으로 작성
상한
VPC당 active peering 기본 50개(최대 125개까지 상향), 두 VPC 사이에는 1개만
static route만
peering attachment를 향한 static route를 TGW route table에 직접 추가 (BGP 전파 없음)
암호화, 백본
리전 간 트래픽은 AWS 백본에서 AES-256으로 암호화, 인터넷을 거치지 않음
리전을 넘지 못하는 것
SG 참조, Route 53 Resolver 기반 상대 리전 private DNS 해석은 peering 너머로 동작하지 않음
상한
TGW 쌍당 peering 1개, TGW당 peering 기본 50개, MTU 8500
# us-east-1 TGW route table (us-west-2는 대칭)
10.0.0.0/16 → vpc attachment (local VPC, propagation)
10.1.0.0/16 → peering attachment (static, us-west-2)
정책 기반
core network policy(JSON)에 리전, segment, attachment 규칙을 선언하면 Cloud WAN이 구성
동적 라우팅
리전마다 core network edge(CNE)가 생성되고 CNE 간 경로를 자동 교환
segment 격리
prod, dev, shared 같은 segment로 리전을 가로질러 격리, 태그로 자동 매핑
언제 고려
리전이 3개 이상으로 늘거나 segment 정책을 중앙에서 관리해야 할 때. 기존 TGW와 peering으로 공존 가능

Key Takeaways

1목적이 패턴을 정한다
가용성, 지연, 레지던시 중 무엇이 목표인지가 Active-Active와 Active-Passive를 가른다
2평소의 지연이 진짜 비용
PACELC 관점에서 데이터마다 Strong, Session, Eventual을 고른다
3쓰기는 한 곳에 모은다
Write-Primary / Read-Local은 충돌을 없애는 대신 서부 쓰기 지연을 받아들인다
4네트워크는 처음에 정한다
겹치지 않는 CIDR, private 진입, TGW static route는 나중에 바꾸기 가장 어렵다
