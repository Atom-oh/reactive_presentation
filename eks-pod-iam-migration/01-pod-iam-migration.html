권한 합집합

  • 노드에 뜰 수 있는 모든 워크로드의 권한이 노드 Role에 모임

폭발 반경

  • 권한이 필요 없는 Pod 하나만 뚫려도 노드 Role 전체 노출

감사 불가

  • CloudTrail에는 NodeRole/i-xxx만 남음: 어느 Pod인지 모름

SDK는 자격 증명을 어디서 찾나: default credential chain

1. 환경 변수 정적 키 AWS_ACCESS_KEY_ID
2. 공유 config / profile ~/.aws
3. Web identity (IRSA) AWS_WEB_IDENTITY_TOKEN_FILE
4. Container credentials (Pod Identity) AWS_CONTAINER_CREDENTIALS_FULL_URI
5. IMDS 169.254.169.254 → 노드 Role

순서는 AWS SDK 표준 credential provider 기준이며 언어별 SDK 문서로 확인합니다. Webhook은 env를 Pod 생성 시 주입하므로 설정을 바꾸면 재시작이 필요합니다.

IMDSv2 hop limit: Pod 네트워크까지 응답이 닿는가

IRSA 동작 원리: OIDC 신뢰 + AssumeRoleWithWebIdentity

Pod Identity 동작 원리: Agent + EKS Auth API

설정 비교: trust policy와 매핑 위치

IRSA: 클러스터별 OIDC provider를 신뢰

{
  "Principal": { "Federated": "arn:aws:iam::111122223333:
      oidc-provider/oidc.eks.<region>.amazonaws.com/id/<ID>" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": { "StringEquals": {
    "…/id/<ID>:sub": "system:serviceaccount:demo-irsa:s3-reader",
    "…/id/<ID>:aud": "sts.amazonaws.com" } }
}
# 매핑 = SA annotation
kubectl -n demo-irsa annotate sa s3-reader \
  eks.amazonaws.com/role-arn=arn:aws:iam::…:role/irsa-s3-reader

Pod Identity: 공통 서비스 principal을 신뢰

{
  "Principal": { "Service": "pods.eks.amazonaws.com" },
  "Action": ["sts:AssumeRole", "sts:TagSession"]
}
// 클러스터 정보 없음 → 여러 클러스터에서 그대로 재사용
# 매핑 = EKS API association (SA 객체는 그대로)
aws eks create-pod-identity-association \
  --cluster-name pod-iam-demo --namespace demo-podid \
  --service-account s3-reader --role-arn arn:aws:iam::…:role/podid-s3-reader

Session tags kubernetes-namespace, kubernetes-service-account, eks-cluster-name 등으로 ABAC: ${aws:PrincipalTag/kubernetes-namespace}/*

비교 데모 시뮬레이터: 같은 워크로드, 세 가지 신원

  --nodegroup-name $NODEGROUP_NAME --query nodegroup.nodeRole --output text | awk -F/ '{print $NF}')

  --policy-document "$(render policies/s3-read.json.tpl)"

  render manifests/workload.yaml.tpl | sed "s/NAMESPACE/$ns/g" | kubectl apply -f -

왜 t2에서 안 바뀌나

  • SDK chain에서 web identity(3번)가 container credentials(4번)보다 먼저

롤백

  • t3 이후 문제 시 annotation 재부착 + 재시작. trust에 OIDC가 남아 있어 즉시 복구

정리

노드 Role

  • kubelet·ECR pull·(CNI) 같은 노드 기능만
  • 앱 권한은 0
  • IMDSv2 + hop limit 1

IRSA

  • Fargate, EKS 밖 클러스터
  • sub·aud를 StringEquals로 고정
  • 클러스터마다 OIDC provider

Pod Identity

  • EKS on EC2 신규 기본값
  • trust 재사용, association으로 매핑
  • session tag ABAC
  • CloudTrail로 노드 Role 사용처 인벤토리
  • 워크로드별 전용 SA + 최소 권한 Role
  • 전환 후 CloudTrail 주체 확인 → 노드 Role 정리 → IMDS 차단
