Block 2: 네트워킹 & Hybrid Nodes Gateway

누가 세션을 열고, Pod CIDR은 어떻게 도달하며, Gateway는 언제 쓰는가

연결이 먼저, 쿠버네티스는 그다음

그림의 Gateway = VGW/TGW 같은 사설 연결 게이트웨이입니다. 뒤에 나올 Hybrid Nodes Gateway와는 다른 물건입니다.
사설 연결
Direct Connect 또는 Site-to-Site VPN. 공용 인터넷 경로와 사설 경로를 구분해 설계
권장 품질
대역폭 ≥100 Mbps, RTT ≤200 ms (AWS 일반 권장, 보장값 아님)
양방향 route
VPC → remote node/Pod CIDR, 온프렘 → VPC CIDR. 한쪽만 있으면 join 후 logs/exec가 막힘

CIDR 설계: 겹치면 모든 게 막힌다

  • Remote node CIDR 최대 15개, remote Pod CIDR 최대 15개
  • IPv4 전용, RFC1918 또는 CGNAT(100.64.0.0/10) 범위
  • node/Pod CIDR끼리, 그리고 VPC, Service CIDR과도 겹치지 않을 것
  • 기존 클러스터에도 remote network 구성을 추가할 수 있음 (생성 시점 전용 아님)
    "remoteNetworkConfig": { "remoteNodeNetworks": [{ "cidrs": ["10.80.0.0/16"] }], "remotePodNetworks": [{ "cidrs": ["10.85.0.0/16"] }] }
  • Pod CIDR을 라우팅 가능하게 만들지(BGP/static) 결정, webhook, Cloud↔Hybrid Pod 통신이 여기에 달림
  • Cilium cluster-pool: 기존 항목, MaskSize 변경 금지, 확장은 새 항목 추가 (Cilium 문서 기준)

443은 안에서 열고, 10250은 밖에서 온다

그림 속 Gateway도 사설 연결 게이트웨이입니다 (Hybrid Nodes Gateway 아님).
온프렘이 연다 (outbound)
kubelet, Pod → Kubernetes API, TCP 443. 노드가 먼저 연결을 시작
AWS가 연다 (inbound)
CP → kubelet TCP 10250 (logs/exec/port-forward), CP → webhook Pod의 실제 설정 port
응답 허용 ≠ 신규 inbound 허용
443 세션의 stateful return이 10250 신규 연결을 열어 주지 않음. 별도 방화벽 규칙 필요

kubelet과 CP, 세션 방향이 다르다

public/private 중 하나를 선택: 경로가 다르므로 endpoint 설정에 따라 방화벽, DNS가 달라집니다. EKS 관리 PrivateLink(eks)와 Kubernetes API endpoint는 별개입니다.
보고된 node IP의 TCP 10250으로 CP ENI에서 접속합니다. return route, 방화벽, kubelet 인증이 모두 필요하고, logs/exec/port-forward에 쓰입니다.
한 줄 정리
443은 온프렘이 열고, 10250은 CP가 엽니다, 같은 노드라도 방화벽 규칙의 방향이 다릅니다.

Pod→API: Service 변환과 SNAT

그림은 kube-proxy/iptables 기준의 설명용입니다. Cilium eBPF kube-proxy replacement에서는 처리 방식이 다르고, 번호도 보편적 hook 순서가 아닙니다.
SNAT 있음
응답이 node 주소로 돌아오고 conntrack이 역변환. Pod CIDR return route 불필요
SNAT 없음
Pod 주소 그대로 나가므로 VPC → Pod CIDR return route 필요 (routable Pod 설계)
Service IP를 쓰는 Pod는 선택한 API endpoint로의 Service 변환이 먼저 일어남

웹훅: CP가 Pod IP로 직접 들어온다

Pod CIDR route가 있어야 합니다. CP ENI → VPC route → 사설 연결 → 온프렘 라우터 → node → Pod. 포트는 실제 설정한 webhook port이며 "8443 이상 전체"가 아닙니다.
① VPC route
pod CIDR마다 route 1건 → Gateway leader ENI
② VXLAN
hybrid_vxlan0, VNI 2, UDP 8472 → hybrid node IP
③ Cilium
VTEP decap 후 webhook Pod 전달. 응답은 CiliumVTEPConfig 경로로 반환
Gateway 설치만으로 완성되지 않습니다. remote Pod network, CP subnet route, webhook Service/endpoint/TLS, 방화벽, return path를 확인해야 합니다. Pod를 직접 라우팅해도 webhook은 지원됩니다.
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: eks.amazonaws.com/compute-type
          operator: NotIn
          values:
          - hybrid
webhook을 cloud 노드에 두면 CP → 온프렘 Pod 경로가 필요 없습니다. Pod-template affinity 조각이며, AWS Load Balancer Controller, cert-manager 등의 webhook 배치를 검토하세요. 단 kubelet 10250 inbound는 별개입니다.
한 줄 정리
CP가 Pod에 닿지 못하면 해당 webhook 호출이 실패합니다, Pod route를 만들거나(BGP/static/Gateway) webhook을 cloud에 두세요.

업그레이드는 교체가 기본이다

  • 권장: 새 호스트를 준비해 전환: 새 노드를 초기화, 검증한 뒤 이전 호스트를 비웁니다 (이전 호스트는 검증 완료까지 보존)
  • in-place: 비운(cordon + drain) 호스트에서 nodeadm upgrade 실행. 중단 작업이며 트랜잭션식 다운그레이드가 아님
  • kubelet은 API 서버보다 새 버전일 수 없고, n-3까지 뒤처질 수 있음 (계속 유지하라는 권장은 아님)
  • 뒤처진 노드를 먼저 현재 컨트롤 플레인 마이너로 맞춘 뒤, 다음 마이너는 컨트롤 플레인부터
sudo /usr/local/bin/nodeadm upgrade "$TARGET_MINOR" \ -c file:///etc/eks/nodeconfig.yaml --timeout 20m
  1. 현재 values, Helm revision 저장, 버전별 업그레이드 문서 확인
  2. Hybrid 노드로 한정한 별도 preflight 릴리스 실행 (preflight.enabled=true, agent=false, operator.enabled=false)
  3. DaemonSet 커버리지와 검증 Deployment readiness를 둘 다 대기
  4. 통과 후 preflight 릴리스만 제거
  5. 기존 values + 적절한 upgradeCompatibility로 업그레이드, 한 마이너씩

마이너 버전 사이에 --reuse-values를 쓰지 않습니다.

  • nodeadm upgrade --rollback은 없습니다
  • 실패 시 해당 노드의 cordon 유지, 나머지 작업 중단
  • 현재 컨트롤 플레인과 호환되는 승인된 이미지/버전의 호스트로 교체
  • /var/lib/kubelet, /etc/kubernetes 재귀 삭제는 롤백 단계가 아님
  • uninstall은 SSM 등록도 해제하므로 무조건 uninstall/reinstall 반복 금지
  • Cilium만 명시한 Helm revision으로 helm rollback 가능하나 데이터 경로 복구를 보장하지 않음 (CRD 호환성 검토 필요)

1.37 업그레이드 전 필수 점검

  • 1.37에서 SELinuxMount가 기본 활성화: SELinux가 켜진 노드(예: RHEL)만 영향
  • CSI driver가 seLinuxMount: true이고 Pod에 seLinuxOptions가 있으면 mount -o context=LABEL로 마운트
  • 같은 노드에서 한 volume을 다른 label, seLinuxChangePolicy, 권한 수준으로 공유하면 뒤에 뜬 Pod가 ContainerCreating에 멈춤
  • 공유 Pod끼리 seLinuxOptions.level과 seLinuxChangePolicy를 맞추고, privileged와 unprivileged가 섞이면 Recursive로 지정
kubectl get csidriver \ -o custom-columns=NAME:.metadata.name,SELINUXMOUNT:.spec.seLinuxMount
  • deprecated cAdvisor flag가 남아 있으면 kubelet이 기동하지 않음 (--housekeeping-interval만 예외)
  • eventRecordQPS: 0은 이제 무제한: 이전 동작(초당 5개)을 유지하려면 5로 변경
  • metric 제거: container_cpu_load_average_10s, container_cpu_load_d_average_10s, container_tasks_state → 대시보드, 알람 수정
  • kubelet이 시작할 때 전체 설정을 로그에 남김 → 노드 로그 읽기 권한 제한

"EKS 최적화 AMI는 영향 없음"은 Hybrid 노드에 해당하지 않습니다. NodeConfig의 kubelet.flags, kubelet.config와 골든 이미지에 넣은 인자를 점검합니다.

  • 1.35: cgroup v1 노드에서 kubelet 기동 거부 (기본값), Ubuntu 20.04, RHEL 8은 기본이 cgroup v1
  • 1.35: kubelet --pod-infra-container-image flag 제거, NodeConfig kubelet.flags, 골든 이미지에서 삭제
  • 1.36: containerd 2.0 이상 필요 (1.35가 containerd 1.x 마지막)
  • 1.36: gitRepo volume 비활성, StrictIPCIDRValidation 기본 활성, Service externalIPs deprecated
  • 업그레이드는 한 마이너씩, 이전 버전의 변경 사항도 모두 적용되므로 함께 점검

위 항목은 업그레이드 전에 끝낼 일입니다. 노드에서 확인하지 못했다면 새 호스트로 먼저 검증합니다.

제한망 ≠ 단절: AWS 연결은 필수

  • 제한망 = 퍼블릭 인터넷은 제한, 하지만 EKS 컨트롤 플레인과 자격 증명용 AWS 서비스 연결은 계속 필요
  • 물리적 단절(DDIL)은 Hybrid Nodes의 지원 운영 모델이 아님, IAM Roles Anywhere도 CreateSession 호출이 필요
  • 온프레미스에서 S3에는 Interface 엔드포인트 사용 (gateway 엔드포인트는 온프레미스에서 직접 접근 불가)
  • 소프트웨어는 승인한 manifest를 자체 미러에서 사용, artifact와 manifest는 검토한 절차로 직접 준비 (nodeadm은 SigV4 서명 없는 HTTP(S)로 다운로드)
sudo nodeadm install "$APPROVED_PATCH" --region "$REGION" \ --credential-provider iam-ra --containerd-source none \ --manifest-override "file://$LOCAL_MANIFEST" --private-mode sudo nodeadm init --config-source file:///etc/eks/nodeconfig.yaml \ --manifest-override file:///etc/eks/manifest.json --private-mode

--private-mode는 --manifest-override가 필수이며 OS 패키지 설치를 건너뜁니다. containerd, runc, iptables, CA 인증서는 미리 설치해 두세요.

hybrid-assets.eks.amazonaws.com을 Route 53 PHZ에서 S3로 CNAME 해도 투명 미러가 되지 않습니다.

  • TLS 인증서, SNI 호스트명 불일치
  • HTTP Host 헤더와 S3 버킷, 키 매핑 불일치
  • 요청 권한(서명) 미제공

TLS 검사를 끄는 방식으로 해결하지 않습니다. 대신 통제된 프록시, 사전 설치 이미지, 실제 미러 URL의 manifest override 중 선택하세요.

크리덴셜 만료를 먼저 감시하라

  • 활성화 기본 만료 24시간, 최대 30일, RegistrationLimit 1–1000
  • 활성화 만료는 신규 등록만 제한, 이미 등록한 노드는 영향 없음
  • 세션 자격 증명은 고정 1시간, 에이전트가 갱신

  • 세션 기본 1시간, 범위 15분–12시간, 역할 MaxSessionDuration 이하

# 만료까지 30일 미만이면 실패(종료 코드 1) openssl x509 -in "$CERT_PATH" -checkend 2592000 -noout
  • 인증서 갱신은 기존 PKI/CA 정책으로, 후보 인증서는 활성 파일과 분리 검증 후 교체
  • kubelet 재시작만으로 X.509가 갱신되지 않음

배치는 label 하나에서 시작한다

Hybrid 노드에는 eks.amazonaws.com/compute-type=hybrid label이 자동으로 붙습니다. 위치 label(example.com/location)은 노드 소유자가 직접 부여합니다.

nodeSelector: eks.amazonaws.com/compute-type: hybrid example.com/location: onprem tolerations: # hybrid taint를 쓰는 경우에만 필요 - key: eks.amazonaws.com/compute-type operator: Equal value: hybrid effect: NoSchedule
affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: # term끼리 OR, term 안은 AND - matchExpressions: - {key: eks.amazonaws.com/compute-type, operator: In, values: [hybrid]} - {key: example.com/location, operator: In, values: [onprem]} - matchExpressions: - {key: example.com/location, operator: In, values: [cloud]} - {key: karpenter.sh/nodepool, operator: In, values: [cloud-burst-pool]} preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 preference: matchExpressions: - {key: example.com/location, operator: In, values: [onprem]}

Hybrid taint는 선택 사항입니다. 자동으로 붙지 않으며, 추가 전에 CNI, DNS, GPU 인프라 Pod의 toleration부터 확인합니다.

kubectl taint node "$NODE_NAME" \ eks.amazonaws.com/compute-type=hybrid:NoSchedule

NoSchedule은 새 스케줄링에만 영향을 줍니다. label이나 required affinity를 바꿔도 이미 실행 중인 Pod는 자동으로 이동하지 않습니다.

topologySpreadConstraints: - maxSkew: 2 topologyKey: topology.kubernetes.io/zone whenUnsatisfiable: ScheduleAnyway labelSelector: matchLabels: app: hybrid-burst-app

ScheduleAnyway는 점수 선호이며 maxSkew를 넘을 수 있습니다. zone label은 실제 장애 도메인에만 부여하고, 모든 Hybrid 호스트를 AWS AZ로 표시하지 않습니다.

외부 노출은 IP target과 BGP로

자체 관리형 AWS Load Balancer Controller는 도달 가능한 Hybrid Pod IP를 target으로 등록할 수 있습니다. ALB는 alb.ingress.kubernetes.io/target-type: ip, NLB는 service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip와 loadBalancerClass: service.k8s.aws/nlb를 사용합니다.

route, 반환 경로, security group/firewall, remote Pod network 구성이 맞아야 합니다. 컨트롤러는 cloud node에 두는 설계를 권장합니다.

nodeSelector: example.com/location: cloud
apiVersion: cilium.io/v2 kind: CiliumLoadBalancerIPPool metadata: name: on-prem-pool spec: blocks: - cidr: "10.90.0.0/24" serviceSelector: matchLabels: exposure: onprem-bgp

예시 CIDR은 인벤토리에서 예약한 비중복 대역으로 바꿉니다. IP 할당이 라우터 광고나 통신 성공을 보장하지는 않습니다.

apiVersion: cilium.io/v2 kind: CiliumBGPAdvertisement metadata: name: hybrid-service-advertisement labels: advertise: hybrid-services spec: advertisements: - advertisementType: Service service: addresses: [LoadBalancerIP] selector: matchLabels: exposure: onprem-bgp

CiliumBGPClusterConfig, CiliumBGPPeerConfig와 함께 구성합니다. 세션, 수락된 라우트, next hop, 반환 경로를 확인해야 완성입니다.

cilium.io/v2 BGP CRD는 Cilium 1.18 기준입니다. 1.17.x 클러스터는 Block 2 예제처럼 v2alpha1을 사용합니다.

Cilium Ingress와 Gateway API는 L7 proxy가 필요합니다. 그러나 Hybrid Nodes Gateway의 필수 설정은 vtep.enabled=true, l7Proxy=false이므로 같은 Cilium 설치에 함께 적용할 수 없습니다. 기능을 켜기 전에 네트워크 설계를 먼저 선택합니다.

Pod Identity는 6단계 체크

  • (Ubuntu, RHEL, AL2023) 호스트 NodeConfig에 credentials file 활성화
    spec: hybrid: enableCredentialsFile: true
  • 호스트마다 계획된 nodeadm init을 다시 실행 (한 호스트씩 검증)
  • Pod Identity Agent add-on에 Hybrid DaemonSet 활성화
    {"daemonsets": {"hybrid": {"create": true}}}
  • add-on 버전 확인: 일반 OS 1.3.3-eksbuild.1 이상. Bottlerocket은 add-on 1.3.7-eksbuild.2 + OS 1.39.0 이상이며, 1–3 대신 bootstrap 명령에 --enable-credentials-file=true, DaemonSet 키는 hybrid-bottlerocket
  • eks-auth 서비스 경로 + 노드 역할의 eks-auth:AssumeRoleForPodIdentity 권한
  • 워크로드별 Pod Identity association (namespace, ServiceAccount, IAM role 신뢰, 권한)

'endpoint'는 세 가지를 뜻한다

Kubernetes API private endpoint
kubelet, Pod, 운영자가 TCP 443으로 접근하는 사설 진입점. control plane의 온프레미스행 연결을 없애지 않습니다.
EKS control-plane ENI
API server와 VPC, remote node/Pod network 사이의 연결 지점. DLP나 망연계 장비가 아닙니다.
interface VPC endpoint (PrivateLink)
eks, ssm, rolesanywhere 등 AWS 서비스 API용. kubelet 연결의 중계 서비스가 아닙니다.
세션 A: 노드가 시작 kubelet → API (TCP 443)
세션 B: API server가 시작 API → kubelet (TCP 10250), 사용 시 webhook 포트도 온프레미스 inbound
private endpoint ≠ 망분리 준수 노드가 먼저 연결했다는 이유로 control plane발 연결이 사라지지 않습니다.

K8s 객체, Secret, 로그까지 온프레미스에만AWS control plane 구성과 충돌 가능

Direct Connect는 기본적으로 전송 중 암호화를 제공하지 않습니다. Kubernetes API, kubelet의 TLS와 인증을 유지하고, 회선 구간 암호화가 필요하면 IPsec over DX 또는 MACsec 적용 범위를 검토합니다.

MACsec은 지원 DX 연결의 링크 보호이며 종단 간 TLS와 범위가 다릅니다. Hybrid Nodes Gateway(VXLAN)도 자체 암호화가 없습니다.

get nodes/proxy를 단순 조회 권한으로 분류하지 않습니다. kubelet API를 통한 컨테이너 명령 실행이 가능할 수 있고, Kubernetes audit, admission 경로를 우회할 수 있습니다.

pods/log, pods/exec, pods/attach, pods/portforward, nodes/proxy와 workload 생성 권한을 함께 검토합니다.

핵심 요약: 4개 블록, 6가지

1. 구조와 전제
AWS가 control plane을, 사용자가 host, 연결, workload를 운영합니다. AWS와의 사설 양방향 연결이 필수입니다.
2. 네트워크
kubelet 10250과 webhook은 AWS에서 시작하는 inbound입니다. Gateway는 선택이며 직접 라우팅도 유효합니다.
3. 라이프사이클
nodeadm으로 설치, join, 업그레이드합니다. rollback 명령이 없으므로 업그레이드, 복구 모두 in-place보다 호스트 교체를 우선합니다.
4. 워크로드 배치
compute-type label로 배치하고, 버스팅은 Pending Pod가 트리거하며 자동 복귀는 없습니다.
5. GPU와 관측성
GPU마다 할당 관리자는 하나, 신규 1.34 이상은 DRA 권고. hybrid 지표는 relabel로 구분합니다.
6. 보안과 비용
private endpoint는 망분리 준수의 증거가 아닙니다. 비용은 보고된 vCPU-hour 구간 과금입니다.
