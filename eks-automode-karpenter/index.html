1부: Pending Pod가 노드를 부른다

고정된 노드 그룹 중심

  • 인스턴스 유형과 크기를 그룹마다 미리 정함
  • 워크로드 모양이 바뀌면 그룹을 새로 설계
  • 비어 가는 노드를 줄이는 판단은 사람이 함
  • AMI 교체와 노드 수명 관리도 별도 작업

Pending Pod 기반 프로비저닝

  • 스케줄되지 못한 Pod의 요구 사항이 수요 신호
  • requirements를 만족하는 인스턴스 유형 중에서 선택
  • 남는 노드는 consolidation으로 회수
  • 설정이나 AMI가 바뀌면 Drift, 오래되면 만료로 교체
핵심 질문이 바뀝니다: "몇 대를 띄울까"가 아니라 "어떤 조건의 노드를 허용하고, 언제 바꿔도 되는가"를 선언합니다.

제어 루프: 누가 무엇을 하나

1Pod가 Pending자리를 찾지 못한 Pod를 unschedulable로 표시kube-scheduler
2NodeClaim 생성NodePool 조건 안에서 인스턴스 후보를 계산하고 NodeClaim을 만듦Karpenter controller
3EC2 시작NodeClass의 subnet, SG, AMI로 인스턴스를 띄움Karpenter cloud provider, EC2
4노드 Readykubelet이 클러스터에 등록, NodeClaim이 Node와 연결kubelet
5Pod 바인딩새 노드에 Pod를 배치kube-scheduler
Karpenter는 Pod를 배치하지 않음
노드를 만들 뿐이고, 바인딩은 여전히 kube-scheduler가 합니다.
NodeClaim이 노드 한 대의 기록
교체, 만료, 중단 판단도 NodeClaim 단위로 이루어집니다.
Auto Mode도 같은 루프
2번과 3번을 AWS가 운영하는 관리형 Karpenter가 맡습니다.

2부: NodePool과 NodeClass의 분업

karpenter.sh/v1, kind: NodePool
  • template.spec.requirements: 허용할 인스턴스 조건
  • disruption: consolidation 정책, budget
  • template.spec.expireAfter, terminationGracePeriod
  • limits, weight, nodeClassRef
무엇을, 언제 바꿀지
어떤 노드를 허용하고 언제 회수, 교체할지를 정합니다. Auto Mode와 직접 운영이 같은 API를 씁니다.
karpenter.k8s.aws/v1, kind: EC2NodeClass
  • amiSelectorTerms: alias, id, name, tags, ssmParameter
  • subnetSelectorTerms, securityGroupSelectorTerms
  • role 또는 instanceProfile
  • kubelet, userData
어디에, 어떤 이미지로
AMI, 네트워크, IAM, 부팅 설정을 사용자가 정합니다. Karpenter가 launch template을 만듭니다.
eks.amazonaws.com/v1, kind: NodeClass
  • role 또는 instanceProfile
  • subnetSelectorTerms, securityGroupSelectorTerms
  • ephemeralStorage, advancedNetworking
  • advancedCompute: kubelet, sysctl, hugepages 일부
AMI 필드가 없음
OS는 AWS가 고르는 Bottlerocket 변형입니다. launch template, userData, SSH, SSM도 쓰지 않습니다.
라벨 접두사도 다름: 직접 운영은 karpenter.k8s.aws/instance-*, Auto Mode는 eks.amazonaws.com/instance-*. NodePool을 옮길 때 requirements 키를 바꿔야 합니다.

노드를 고르고, 줄이고, 바꾸는 규칙

Drift와 만료: 노드는 결국 교체된다

Drift를 일으킴
NodePool template과 NodeClass spec 변경. requirements, subnet, SG, AMI는 resolve 결과로 비교
Drift를 일으키지 않음
spec.weight, spec.limits, spec.disruption.*
AMI는 alias로 고정
al2023@v20261012처럼 pin. @latest는 새 AMI마다 전체 Drift라 프로덕션 비권장
Auto Mode는 AMI가 Drift 신호
새 AMI가 대략 주 1회 나오고 Drift로 롤링. advancedCompute 변경도 in-place 없이 Drift
항목Self-managed v1.15Auto Mode

Spot 중단: 2분 경고는 누가 받나

Self-managed: SQS와 EventBridge를 직접

  • SQS interruption queue, Helm settings.interruptionQueue로 연결
  • EventBridge rule 5개: Spot Interruption Warning, Rebalance, State-change, AWS Health, Capacity Reservation Interruption
  • Spot 경고를 받으면 drain과 새 노드 생성을 병행
  • Rebalance Recommendation은 이벤트 기록만 함

Auto Mode: AWS가 처리

  • Spot 중단 알림, EC2 health 이벤트, 상태 검사 실패를 자동 처리
  • 사용자가 SQS나 EventBridge를 구성하지 않음
  • ARC zonal shift 시 해당 AZ의 노드 생성과 자발적 disruption 중지
queue를 안 붙이면 비활성
self-managed에서 interruptionQueue가 없으면 interruption 처리가 꺼집니다.
FIS EC2 action은 Auto Mode 미지원
SendSpotInstanceInterruptions 포함. Spot 중단 리허설은 self-managed 노드에서 합니다.

Auto Mode인가, 직접 운영인가

직접 운영 쪽 신호

  • custom AMI, userData, launch template, SSH나 SSM 접속이 필요
  • kubelet, sysctl 요구가 advancedCompute 지원 필드를 벗어남
  • Windows 노드, DRA, 대체 CNI 필요 (Security Groups per Pod는 podSecurityGroupSelectorTerms로 대체)
  • feature gate 기능이나 FIS EC2 장애 주입 테스트가 필요

Auto Mode 쪽 신호

  • Karpenter minor마다 CRD와 breaking change를 따라갈 인력이 부족
  • CNI, CoreDNS, EBS CSI, LB controller 운영을 줄이고 싶음
  • 주간 AMI 교체와 21일 수명 상한을 보안 기준으로 받아들일 수 있음
  • 인스턴스당 관리비가 운영 시간 절감보다 작다고 판단

왼쪽이 하나라도 필수라면: 그 워크로드는 self-managed가 맞습니다. 클러스터를 나누거나, 마이그레이션 중에만 NodePool로 분리해 공존합니다.

5부: 데모 영상

같은 조건, 두 클러스터: 스케일 아웃, Consolidation, Drift, Spot 중단

데모 환경: 같은 VPC, 같은 NodePool 조건

akd-auto: EKS Auto Mode
  • 노드 OS: Bottlerocket (EKS Auto, Standard) 2026.10.9
  • NodeClass demo (eks.amazonaws.com/v1)
  • 정책 미지정 시 라이브 값: Balanced, expireAfter 336h
akd-karp: 직접 설치 Karpenter 1.15.0
  • 노드 OS: Amazon Linux 2023 (AMI v20261003으로 시작)
  • EC2NodeClass default + interruption queue (SQS)
  • 정책 미지정 시 라이브 값: WhenEmptyOrUnderutilized, expireAfter 720h
공통 조건: EKS 1.37, ap-northeast-2, 데모 VPC의 private 서브넷 2개(2a, 2b). NodePool demo: on-demand, c/m/r 계열, generation 5 초과, amd64, consolidateAfter 30s, budget nodes: "1". 워크로드: pause 컨테이너, replica당 1 vCPU / 1.5Gi
노드에 공인 IP 없음. API endpoint는 작업 PC의 출구 IP 하나만 허용했습니다.

score 0.50 >= threshold 0.50

절감 비율을 disruption 비율로 나눈 점수가 임계값 이상일 때만 실행합니다. 노드 한 대뿐이라 disruption 100%였고, 절감 50%로 겨우 통과했습니다.
시점은 비교하지 않는다
녹화 회차는 Auto Mode +67초, Karpenter +75초에 첫 이동. 앞선 회차는 Karpenter 약 1분, Auto Mode 약 5분 30초 뒤였습니다. 정책의 속도 차이로 해석하지 않습니다.

6부: 오늘 가져갈 다섯 가지

1. 판단은 같은 Karpenter
Auto Mode도 같은 조건에 같은 노드를 골랐습니다. 차이는 누가 운영하느냐입니다.
2. 1.37 기본값을 명시
비워 두면 Auto Mode는 Balanced, Karpenter는 WhenEmptyOrUnderutilized입니다.
3. 버전 순서
직접 운영은 Karpenter 1.15.x와 CRD를 먼저, 그다음 Kubernetes 1.37입니다.
4. 교체는 budget으로
AMI는 버전을 고정하고, budget과 PDB로 교체 속도를 정합니다.
5. 배치가 가용성
Spot 중단에 견디는 힘은 replica 분산에서 나옵니다.
