원칙
저장소마다 복제 모델, 지연, 장애 시 손실이 다릅니다. 서비스별로 "쓰기 위치"와 "허용 RPO"를 먼저 정하고 저장소를 고릅니다.

복제 모델은 세 가지, 대가는 지연

← 강한 일관성, 쓰기 지연 큼쓰기 지연 작음, 결과적 일관성 →
① 동기 multi-Region
  • 커밋 전에 다른 리전에 기록
  • Aurora DSQL, DynamoDB MRSC
  • RPO 0, 대신 쓰기마다 리전 간 왕복
② 단일 writer + 비동기 복제
  • 쓰기는 primary 한 곳
  • Aurora Global DB, DocumentDB Global, Valkey Global Datastore
  • 읽기는 로컬, 장애 시 lag만큼 손실 가능
③ multi-writer + 비동기
  • 모든 리전이 로컬 쓰기
  • DynamoDB MREC, MSK active-active
  • 충돌 해소 규칙(last writer wins)을 앱이 수용
설계 규칙
쓰기 경로는 일관성을, 읽기 경로는 지연을 우선합니다. 같은 서비스 안에서도 쓰기와 읽기의 모델이 다를 수 있습니다.

Write Forwarding은 대신 전달한다

us-west-2
order-service
secondary reader endpoint
→ DML 전달 →
us-east-1

→ 스토리지 복제 →
us-west-2
변경 반영 후 읽기
DML만 전달되고, 전달된 쓰기마다 리전 간 왕복이 붙습니다. statement가 많은 긴 트랜잭션보다 가끔 발생하는 짧은 쓰기에 적합하며, 지연 수치는 반드시 실측하세요.
값같은 세션의 쓰기다른 세션, 리전의 커밋대기 비용
SESSION (기본)즉시 보임 (복제 대기)기다리지 않음중간
EVENTUAL복제된 뒤에야 보임기다리지 않음가장 낮음
GLOBAL즉시 보임쿼리 시작 시점까지의 모든 커밋을 기다림가장 높음
OFF해당 세션에서 write forwarding 끔
파라미터 apg_write_forward.consistency_mode, 세션 단위로 바꿀 수 있고 재부팅 불필요. 격리 수준은 READ COMMITTED, REPEATABLE READ만 지원 (SERIALIZABLE 불가).
DDL, 권한
CREATE, ALTER, GRANT, REVOKE는 primary에서 직접 실행
세션 제어
SAVEPOINT, LOCK, SET CONSTRAINTS, cursor 미지원
대량 작업
COPY, TRUNCATE, SELECT INTO, VACUUM, ANALYZE 미지원
사용자 정의 함수, 프로시저
지원되지 않으므로 ORM, 마이그레이션 도구의 동작 확인 필요
# secondary 클러스터에서 켜기 (중단, 재부팅 없음, 기본은 꺼짐)
aws rds modify-db-cluster --region us-west-2 \
  --db-cluster-identifier orders-usw2 \
  --enable-global-write-forwarding

# 세션에서 일관성 모드 확인
SHOW apg_write_forward.consistency_mode;
버전: PG 16 이상은 모든 minor, 15는 15.4 이상, 14는 14.9 이상. 상태는 GlobalWriteForwardingStatus로 확인합니다.
한 줄 정리
write forwarding은 "secondary에서 쓰기 가능"이 아니라 "secondary가 대신 전달"입니다. write-heavy 서비스는 primary 리전에 둡니다.

Switchover만 RPO 0이다

동기화 후 전환 → RPO 0
대상 secondary가 완전히 따라잡을 때까지 기다린 뒤 primary를 read-only로 바꾸고 승격
보통 30초 미만
Aurora PostgreSQL 16.8, 15.12, 14.17, 13.20 이상에서 read/write 복구 시간
조건
모든 클러스터가 정상이고 major, minor 버전이 같아야 함. DR 훈련, 리전 순환, failback 용도
# --region 은 현재 primary 리전
# USW2_ARN: us-west-2 secondary 클러스터 ARN
aws rds switchover-global-cluster \
  --region us-east-1 \
  --global-cluster-identifier shop-global \
  --target-db-cluster-identifier "$USW2_ARN"
동기화를 기다리지 않음
미복제 트랜잭션은 새 primary에 없음. old primary 복구 시 rds:unplanned-global-failover-... 스냅샷 시도
write fencing은 best effort
old primary가 잠시 쓰기를 받을 수 있어 split-brain 가능. 앱 쓰기를 먼저 멈추고 DNS 캐시 TTL은 5초 수준으로
복구 후 자동 재편입
old primary 리전이 정상화되면 secondary로 다시 붙음. failback은 switchover로
# --region 은 승격할 secondary 리전
aws rds failover-global-cluster \
  --region us-west-2 \
  --global-cluster-identifier shop-global \
  --target-db-cluster-identifier "$USW2_ARN" \
  --allow-data-loss
관측 메트릭: AuroraGlobalDBRPOLag (ms, secondary 기준)
커밋 진행
lag 10초 < RPO 60초: 최소 1개 secondary가 RPO 안에 있음
리전이 둘뿐이라면
secondary 파라미터 그룹에는 기본값 유지 권장. 그렇지 않으면 failover 직후 새 primary의 커밋이 멈출 수 있음

DynamoDB: MREC와 MRSC 중 고른다

active-active 비동기
모든 replica가 로컬 쓰기, 보통 1초 안에 전파 (SLA 없음)
last writer wins
같은 item을 거의 동시에 쓰면 item 단위로 마지막 쓰기가 이김. 충돌은 기록되지 않음
리전 수 제한 없음
파티션 내 모든 리전에 replica 가능. 트랜잭션은 리전 간 묶여서 복제되지 않음
관측

정확히 3개 리전

동기 쓰기, RPO 0

Key Takeaways

① 쓰기 위치부터 정한다
서비스별 쓰기 리전과 허용 RPO를 정의한 뒤 저장소와 복제 모델을 고릅니다
② 계획 전환과 장애 전환은 다르다
switchover는 RPO 0, failover는 lag만큼 손실. global writer endpoint로 연결을 고정
③ RPO 0은 동기 모델에서만
Aurora DSQL, DynamoDB MRSC. 대신 쓰기 지연, OCC 재시도, 트랜잭션 제약을 수용
④ idempotency와 lag 알람
MSK 재처리, 캐시 stale, 비동기 손실을 견디려면 idempotent API와 lag 메트릭 알람이 기본
