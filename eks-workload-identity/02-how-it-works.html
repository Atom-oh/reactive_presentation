2부: 두 방식은 안에서 어떻게 다른가

IRSA와 EKS Pod Identity를 한 단계씩, 그리고 나란히

IRSA: Pod가 토큰을 들고 STS로 간다

신뢰 준비
클러스터 issuer를 IAM OIDC(OpenID Connect) provider로 한 번 등록
주입
SA 주석을 본 EKS mutating webhook(amazon-eks-pod-identity-webhook)이 env와 토큰 볼륨 추가
교환
Pod가 리전 STS(Security Token Service)와 직접 통신
출처: Amazon EKS User Guide, IAM roles for service accounts

EKS 클러스터마다 OIDC issuer URL이 있습니다. 이 issuer를 계정의 IAM OIDC provider로 등록하면, IAM 역할의 신뢰 정책이 그 provider를 Federated principal로 지정할 수 있습니다. STS는 provider에 등록된 issuer의 공개 키로 Pod 토큰의 서명을 검증합니다. 클러스터를 새로 만들 때마다 provider 등록과 신뢰 정책 수정이 필요합니다.

IRSA 다섯 단계, aud와 sub가 열쇠

Pod Identity: Agent가 대신 묻는다

연결
EKS API의 association, 주석 없음
조회
SDK는 같은 노드의 Agent만 호출
위임
EKS Auth가 역할을 맡고 세션 태그 부착
출처: Amazon EKS User Guide, How EKS Pod Identity works

aws eks create-pod-identity-association으로 만드는 EKS 리소스입니다. 클러스터, namespace, ServiceAccount 조합을 IAM 역할 하나에 연결합니다. Kubernetes 객체에는 주석을 달지 않으며, 클러스터당 association은 5,000개까지 만들 수 있습니다. 생성 직후 몇 초 동안은 새 Pod에 반영되지 않을 수 있습니다(eventual consistency).

169.254.170.23, [fd00:ec2::23]
포트 80, 2703
EKS Auto Mode에는 같은 기능이 내장되어 있습니다.

노드 역할에 남는 권한

eks-auth:AssumeRoleForPodIdentity
AmazonEKSWorkerNodePolicy에 포함. Agent가 EKS Auth를 부르는 데만 씁니다.
Agent는 hostNetwork에서 IMDS로 이 역할의 자격 증명을 받습니다.
앱의 업무 권한은 Pod Identity 역할에 둡니다.
프록시 환경: 169.254.170.23과 [fd00:ec2::23]을 NO_PROXY에 넣어야 SDK 요청이 Agent에 닿습니다.

비교 1: 신뢰와 연결을 거는 위치

IRSA

연결 위치: Kubernetes ServiceAccount 주석
eks.amazonaws.com/role-arn: arn:aws:iam::<ACCOUNT_ID>:role/wid-<run>-irsa
Pod Identity
클러스터 준비: 클러스터마다 Agent 애드온 (Auto Mode는 내장)
연결 위치: EKS API association, Kubernetes 객체 변경 없음
aws eks create-pod-identity-association --namespace wid-<run> --service-account orders-podid --role-arn ...
IRSA: Federated + aud, sub 
{
  "Effect": "Allow",
  "Principal": {"Federated":
    "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/<OIDC_ISSUER>"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {"StringEquals": {
    "<OIDC_ISSUER>:aud": "sts.amazonaws.com",
    "<OIDC_ISSUER>:sub":
      "system:serviceaccount:<NAMESPACE>:<IRSA_SA>"
  }}
}
클러스터가 늘 때마다 이 문장을 추가합니다.
Pod Identity: 서비스 principal 하나 
{
  "Effect": "Allow",
  "Principal": {"Service": "pods.eks.amazonaws.com"},
  "Action": ["sts:AssumeRole", "sts:TagSession"],
  "Condition": {"StringEquals": {
    "aws:RequestTag/eks-cluster-arn": "<CLUSTER_ARN>",
    "aws:RequestTag/kubernetes-namespace": "<NAMESPACE>",
    "aws:RequestTag/kubernetes-service-account":
      "<POD_IDENTITY_SA>"
  }}
}
조건은 선택입니다. 쓰려면 association의 세션 태그를 켠 상태로 둡니다.

신뢰 정책에 클러스터 issuer가 들어가 두 팀이 함께 바꿔야 합니다.
Pod Identity

주석이 남아도 새 Pod는 Pod Identity

IRSA에서 Pod Identity로 옮기는 도중

ServiceAccount orders   # role-arn 주석이 남아 있음
association    orders   ...:role/new-podid

# 새 Pod: EKS 웹훅이 Pod Identity 변수만 주입
AWS_CONTAINER_CREDENTIALS_FULL_URI
AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE
# association 전에 만든 Pod: IRSA 변수 유지
AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE
결정은 SDK 체인이 아니라 주입 단계에서 납니다. 기존 Pod는 재생성 전까지 IRSA입니다.
체인 순서와 헷갈리지 않기: 체인에서는 웹 ID 토큰이 앞이지만, EKS는 한 Pod에 두 변수 세트를 함께 넣지 않습니다.
