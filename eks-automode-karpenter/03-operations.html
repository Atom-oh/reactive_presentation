1.37 업그레이드: Karpenter가 먼저

1Karpenter 1.15.xkarpenter-crd와 controller chart를 함께, 버전 문자열은 1.15.0
2상태 확인EC2NodeClass ValidationSucceeded, 대시보드 label 변경
3컨트롤 플레인 1.37리전 기본은 1.36이라 버전 명시
4노드 AMI 갱신alias pin을 1.37 AMI로 바꾸면 Drift로 롤링, budget 적용
왜 Karpenter가 먼저인가: 1.37 호환 버전은 1.15.x뿐입니다. v1.14 LTS로는 1.36까지만 갈 수 있습니다.
Node Repair가 voluntary로
대체 노드 선 생성, NDB reason Unhealthy. CRD enum이 바뀌므로 CRD를 함께 업그레이드
kubelet 검증이 controller로
apply는 성공, EC2NodeClass가 InvalidKubeletConfiguration으로 NotReady
무시되던 설정 거부
Bottlerocket podsPerCore, clusterDNS 2개 이상은 UnsupportedKubeletConfiguration
메트릭 label 변경
reason 소문자화, consolidation_type은 empty, single, multi, 미분류 error는 unknown
1관리형 구성 요소Karpenter, CNI, CoreDNS 등은 AWS가 업데이트

3NodePool 정책 명시새 NodePool의 기본 Balanced 반영 여부 결정

사용자가 볼 것: PDB가 교체를 막고 있지 않은지, 같은 볼륨을 다른 SELinux 라벨로 공유하는 Pod가 ContainerCreating에 머물지 않는지

Auto Mode인가, 직접 운영인가

직접 운영 쪽 신호

  • custom AMI, userData, launch template, SSH나 SSM 접속이 필요
  • kubelet, sysctl 요구가 advancedCompute 지원 필드를 벗어남
  • Windows 노드, DRA, 대체 CNI 필요 (Security Groups per Pod는 podSecurityGroupSelectorTerms로 대체)
  • feature gate 기능이나 FIS EC2 장애 주입 테스트가 필요

Auto Mode 쪽 신호

  • Karpenter minor마다 CRD와 breaking change를 따라갈 인력이 부족
  • CNI, CoreDNS, EBS CSI, LB controller 운영을 줄이고 싶음
  • 주간 AMI 교체와 21일 수명 상한을 보안 기준으로 받아들일 수 있음
  • 인스턴스당 관리비가 운영 시간 절감보다 작다고 판단
