2부: 실제로 옮기는 절차

공통 다섯 단계, 방식별 명령, 공존, 그리고 IMDS 차단

운영 이전은 다섯 단계, 회수는 맨 뒤

  1. 의존성 조사
    노드 역할 정책과 CloudTrail의 실제 세션 비교. 워커 노드, ECR pull 권한은 유지
  2. 역할과 전용 SA 준비
    리소스 단위로 제한한 워크로드 역할. SDK 최소 버전 확인
  3. 카나리 Pod 새로 생성
    주입된 env 이름, 호출자 ARN, API 성공 확인. 토큰과 키는 로그에 출력하지 않기
  4. 순차 전환 후 회수
    AccessDenied, 갱신, 크론까지 관찰. 노드 역할의 해당 정책 문장만 회수
  5. 노드 접근 제한
    IMDSv2 강제, hop limit 1. hostNetwork Pod는 별도 통제

IRSA로 옮기기: provider, 역할, 주석

준비 (클러스터와 역할마다)
1

클러스터의 IAM OIDC provider 등록

eksctl utils associate-iam-oidc-provider \
  --cluster $CLUSTER --approve
2

역할: Federated 신뢰 + aud, sub 조건

aws iam create-role --role-name orders-irsa \
  --assume-role-policy-document file://trust-irsa.json
aws iam put-role-policy --role-name orders-irsa \
  --policy-name orders-s3 --policy-document file://orders-s3.json
신뢰 정책 JSON은 1부 비교 1. 새 클러스터에서 쓰려면 1과 신뢰 정책 문장을 다시 추가합니다.
워크로드마다
3

ServiceAccount에 주석

kubectl -n orders annotate serviceaccount orders \
  eks.amazonaws.com/role-arn=arn:aws:iam::<ACCOUNT_ID>:role/orders-irsa
4

Pod 재생성과 확인

kubectl -n orders rollout restart deployment/orders
# 카나리 Pod: AWS_ROLE_ARN 주입, 호출자 ARN이 assumed-role/orders-irsa
5

노드 역할에서 그 앱의 정책 문장만 회수

줄여 쓰기: eksctl create iamserviceaccount가 2와 3을 한 번에 합니다. 이미 떠 있는 Pod에는 주입되지 않으니 4의 재생성이 꼭 필요합니다.
출처: Amazon EKS User Guide, IAM roles for service accounts

Pod Identity로 옮기기: Agent와 연결

준비 (클러스터마다 한 번, 역할은 재사용)
1

Agent 애드온 (Auto Mode는 생략)

aws eks create-addon --cluster-name $CLUSTER \
  --addon-name eks-pod-identity-agent
노드 역할에 eks-auth:AssumeRoleForPodIdentity (AmazonEKSWorkerNodePolicy에 포함)
2

역할: 서비스 principal 신뢰

aws iam create-role --role-name orders-podid \
  --assume-role-policy-document file://trust-podid.json
# pods.eks.amazonaws.com, sts:AssumeRole + sts:TagSession
워크로드마다
3

association 생성 (Kubernetes 객체 변경 없음)

aws eks create-pod-identity-association \
  --cluster-name $CLUSTER --namespace orders \
  --service-account orders \
  --role-arn arn:aws:iam::<ACCOUNT_ID>:role/orders-podid
4

Pod 재생성과 확인

kubectl -n orders rollout restart deployment/orders
# AWS_CONTAINER_CREDENTIALS_FULL_URI 주입, 호출자 ARN 확인
5

노드 역할에서 그 앱의 정책 문장만 회수

IRSA에서 옮길 때: 신뢰 정책에 서비스 principal 추가, association, rollout, 확인 뒤 OIDC 신뢰와 SA 주석 정리. eksctl utils migrate-to-pod-identity --cluster $CLUSTER는 --approve 없이 실행하면 계획만 출력합니다.
출처: EKS Pod Identity setup overview, eksctl, EKS Pod Identity Associations

주석이 남아도 새 Pod는 Pod Identity

IRSA에서 Pod Identity로 옮기는 도중

ServiceAccount orders   # role-arn 주석이 남아 있음
association    orders   ...:role/new-podid

# 새 Pod: EKS 웹훅이 Pod Identity 변수만 주입
AWS_CONTAINER_CREDENTIALS_FULL_URI
AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE
# association 전에 만든 Pod: IRSA 변수 유지
AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE
결정은 SDK 체인이 아니라 주입 단계에서 납니다. 기존 Pod는 재생성 전까지 IRSA입니다.
체인 순서와 헷갈리지 않기: 체인에서는 웹 ID 토큰이 앞이지만, EKS는 한 Pod에 두 변수 세트를 함께 넣지 않습니다.

프라이빗 클러스터에서 열어 둘 경로

IRSAPod에서 리전 STS
Pod IdentityAgent에서 EKS Auth (eks-auth)
인터넷 경로가 없으면 VPC 인터페이스 엔드포인트, DNS, 보안 그룹을 각각 확인합니다.
출처: 데모 클러스터 server-side dry run 검증, aws/amazon-eks-pod-identity-webhook (container credentials가 우선), EKS private cluster requirements

마지막에 Pod의 IMDS 길을 닫는다

관리형 노드 그룹

launch template 새 버전에 지정하고 롤링 교체
HttpTokens=required
HttpPutResponseHopLimit=1

Karpenter

EC2NodeClass 기본값이 이미 required, hop limit 1. 2로 바꿔 둔 NodeClass만 되돌림
spec:
  metadataOptions:
    httpTokens: required
    httpPutResponseHopLimit: 1

EKS Auto Mode

IMDSv2와 hop limit 1이 기본 적용
별도 설정 없이 일반 Pod의 IMDS 경로가 닫혀 있습니다.
hostNetwork Pod는 예외: 노드 네트워크를 그대로 쓰므로 hop limit과 관계없이 IMDS에 닿습니다. 별도로 통제합니다.
IMDS 자체는 끄지 않기: Pod Identity Agent도 hostNetwork에서 IMDS로 노드 역할을 받습니다. HttpEndpoint=disabled면 Pod Identity가 멈춥니다.
출처: EKS managed node group launch templates, EKS Best Practices, Identity and Access Management, Karpenter EC2NodeClass
