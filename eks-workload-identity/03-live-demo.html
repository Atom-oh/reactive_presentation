3부: 라이브 데모

같은 앱 세 벌을 노드 역할에서 IRSA와 Pod Identity로

데모 무대: 노드 한 대, 앱 세 벌, 객체 하나

환경

기존 EKS 1.36 클러스터의 전용 노드 그룹 1대, orders 앱 3벌, S3 객체 1개
t3.medium, Private 서브넷, taint 적용. IMDSv2 필수, hop limit 2. 노드 역할에 앱의 s3:GetObject가 붙은 출발점

앱 (세 벌 모두 같은 코드)

3초마다 STS(Security Token Service)에 get-caller-identity로 호출자를 묻고, s3api get-object를 호출해 JSON 한 줄을 남깁니다.
hostNetwork 없는 일반 Pod, Pod 안의 AWS CLI 2.35.11, 자격 증명과 토큰은 출력하지 않음

안전장치

만든 리소스에만 Lab, LabRun 태그를 붙이고 수정 전에 확인합니다.
VPC, 서브넷, 보안 그룹, 애드온, OIDC provider는 만들지 않음. 계정 ID와 OIDC ID는 가려서 출력
# 발표 전 (약 5분)
export AWS_REGION=ap-northeast-2  RUN_ID=d1124
./demo.sh up    "$RUN_ID"
# 두 번째 터미널: 2초마다 갱신되는 표
./demo.sh watch "$RUN_ID"
청중용 실시간 화면 (읽기 전용): https://wid-demo.atomai.click/ CloudFront → VPC origin → internal ALB → 대시보드 Pod. ./demo.sh page-up "$RUN_ID"로 발표 전에 띄움. 발표 중에만 열려 있음
데모 코드와 런북: github.com/Atom-oh/kubernetes-docs, examples/security/eks-workload-identity

0단계: 지금은 셋 다 노드 역할

0
$ ./demo.sh watch "$RUN_ID"   # 이미 실행 중

watch 화면의 기대 값

COPY            CREDENTIALS    ROLE                           S3
orders-legacy   node (IMDS)    wid-d1124-node  ← node         allowed

리허설 화면, RUN_ID=d1124. 맨 오른쪽 AT 열(마지막 로그 시각)은 생략
볼 곳: CREDENTIALS 열은 주입된 변수로 판단한 출처, ROLE 열은 STS가 알려 준 실제 호출자입니다.
의미: 이름이 달라도 세 벌 모두 노드 역할로 같은 객체를 읽고 있습니다.

1단계 migrate-irsa: 주석 하나

1
$ ./demo.sh migrate-irsa "$RUN_ID"
실측 6초

스크립트가 실행하는 것

kubectl -n wid-<run> annotate serviceaccount orders-irsa --overwrite \
  eks.amazonaws.com/role-arn=arn:aws:iam::<ACCOUNT_ID>:role/wid-<run>-irsa
kubectl -n wid-<run> rollout restart deployment/orders-irsa
kubectl -n wid-<run> rollout status  deployment/orders-irsa
IRSA 역할과 IAM OIDC provider는 up에서 이미 준비되어 있습니다.

watch에서 바뀌는 행

orders-irsa     IRSA (STS)     wid-d1124-irsa                 allowed
새 Pod에 주입된 변수: AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE, AWS_STS_REGIONAL_ENDPOINTS
나머지 두 행은 그대로 노드 역할입니다.

2단계 migrate-podid: API 호출 하나

2
$ ./demo.sh migrate-podid "$RUN_ID"
실측 11초 (주입 확인 5초 포함)

스크립트가 실행하는 것

aws eks create-pod-identity-association \
  --cluster-name <cluster> --namespace wid-<run> \
  --service-account orders-podid \
  --role-arn arn:aws:iam::<ACCOUNT_ID>:role/wid-<run>-podid
# 주입될 때까지 Pod 템플릿을 --dry-run=server로 확인
kubectl -n wid-<run> rollout restart deployment/orders-podid

watch에서 바뀌는 행

orders-podid    Pod Identity   wid-d1124-podid                allowed
새 Pod에 주입된 변수: AWS_CONTAINER_CREDENTIALS_FULL_URI, AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE, AWS_STS_REGIONAL_ENDPOINTS
리허설에서 본 eventual consistency: 1회차에서 association 생성 직후 재시작한 Pod에는 변수가 주입되지 않아 노드 역할을 계속 썼습니다. 그래서 스크립트는 admission에서 주입이 보인 뒤에 재시작합니다(2회차와 3회차 모두 생성 5초 뒤 확인).

토큰 iss, 수명같은 클러스터 issuer https://oidc.eks.ap-northeast-2.amazonaws.com/id/<OIDC_ID>. IRSA 86,400초(24시간), Pod Identity 약 22~24시간(웹훅이 무작위 편차를 줌)

diff는 토큰의 claim만 디코딩해 보여 주고, 토큰 원문과 자격 증명은 출력하지 않습니다.

4단계 revoke: 레거시만 13초 뒤 거부

4
$ ./demo.sh revoke "$RUN_ID"
실측 13초 후 거부 (2회 모두)

스크립트가 실행하는 것

aws iam delete-role-policy --role-name wid-<run>-node \
  --policy-name OrdersReadInvoices
# legacy 행이 denied가 될 때까지 대기 (최대 180초)

watch 화면의 기대 값

COPY            CREDENTIALS    ROLE                           S3        AT
orders-legacy   node (IMDS)    wid-d1124-node  ← node       denied    04:12:56
orders-irsa     IRSA (STS)     wid-d1124-irsa                 allowed   04:12:58
orders-podid    Pod Identity   wid-d1124-podid                allowed   04:12:58
revoke 직후 리허설 화면 그대로
IAM 회수도 eventual consistency: 첫 리허설에서 첫 denied 약 4분 30초 뒤에 allowed가 두 번 더 나왔고, 그 직후 다시 확인한 1분 동안(로그 11건)은 모두 denied였습니다. 운영에서는 회수 후 수 분 이상 관찰하고 판단합니다.

5단계 harden (옵션): hop limit 1

5
$ ./demo.sh harden "$RUN_ID"
옵션실측 878초 (약 15분)
revoke 직후 실행만 시작하고, 결과는 리허설 값으로 설명 (선택): 노드 교체에 약 15분이 걸려 발표 시간 안에는 끝나지 않을 수 있습니다. 시간이 남으면 마지막에 watch를 확인합니다.

스크립트가 하는 일

launch template 새 버전(hop limit 1)으로 관리형 노드 그룹을 롤링 교체합니다.
새 노드 추가, 기존 노드 drain, 종료 순서. restore는 hop limit 2로 돌리느라 노드를 한 번 더 교체합니다(실측 578초).

watch 화면의 기대 값

orders-legacy   node (IMDS)    no-credentials                 no-creds
orders-irsa     IRSA (STS)     wid-d1124-irsa                 allowed
orders-podid    Pod Identity   wid-d1124-podid                allowed
레거시 Pod는 IMDS 응답이 차단되어 자격 증명을 아예 받지 못합니다. 리허설 로그 한 줄:
{"src":"imds","role":"no-credentials","s3":"no-creds"}

막히면 이 순서로 본다

  • 여전히 노드 역할이 보인다: Pod를 새로 만들었는지, ServiceAccount 이름, IRSA 주석이나 정확한 association, 주입된 env 이름, SDK 버전
  • Pod Identity로 바꿨는데 IRSA 역할이 보인다: association 전에 만든 Pod라 IRSA 변수를 그대로 가짐. rollout으로 재생성하고, 끝나면 주석 정리
  • IRSA 토큰 교환 실패: 토큰 issuer에 맞는 IAM OIDC provider, 신뢰 정책의 aud와 sub, Pod에서 STS 도달
  • Pod Identity 조회 실패: 그 노드의 Agent, EKS Auth 통신, 노드 역할의 eks-auth 권한, association 전파(수 초), 요청 태그 조건
  • 역할은 맞는데 S3 거부: 객체 ARN, 버킷 정책, SCP(Service Control Policy), 권한 경계, VPC 엔드포인트 정책, SSE-KMS(KMS 키로 서버 측 암호화)면 키 권한
